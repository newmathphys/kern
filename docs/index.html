What K.E.R.N. stands for

K.E.R.N. — KNOWLEDGE EVALUATION AND RESOLUTION NODE
KKnowledge — everything an AI agent produces: code, contracts, tests, AST trees. KERN treats it as a claim, not as a fact. EEvaluation — mathematical checking of that claim: Z3 SMT, an independent proof-DAG checker written in Zig, and theorems in Lean 4. RResolution — resolving the conflict between old and new knowledge in Belnap's four-valued logic, where a contradiction is kept as T ⊔ F = B instead of being silently overwritten. NNode — the single gateway (an L0–L5 firewall): code either reaches production with e = 1 or is blocked with e = 0.

Four traps an AI agent falls into — and how KERN refuses them

  • Vacuous precondition (false ⟹ anything): a contradictory requires would make any broken body "provable" → KERN answers [VACUOUS] precondition is unsatisfiable (empty domain) and keeps the gate closed.
  • Weakening the specification: deleting a failing @kern:ensures is the cheapest cheat → every contract is fingerprinted in docs/contracts.lock.json, and any removal or edit is a hard error (rc = 2).
  • Silent behaviour change during refactoring: no contracts required → KERN checks ∃x: f_old(x) ≠ f_new(x) over all of ℤ and prints the exact input where the two versions disagree.
  • A counterexample that lives only in a log: --emit-pytest turns it into a real regression test that fails on the current code, while --sarif / --github-annotations put it on the exact line inside a pull request.

Defect Journal — when the checks themselves lied

Short entries from docs/METRICS.md; the full registry is defect registry #1–#373. Each entry is a case where a measurement or a harness was wrong — not the code it was checking.

#110 — the mutation score was measured without a solver.

Symptom: the score "dropped" to 77.5 % after the mutator was pointed at 14 files instead of 6. Found by measuring, not guessing: without z3 in PATH the suite reports 263 passed; 8 skipped — and a skipped test cannot kill a mutant. One of those 8 tests had been written specifically to kill the mutant that "survived". Fix: the mutator now requires a solver (--require-solver); the score at that time was 95.0 % (38/40). After the corpus grew to 21 files the full sweep reports 1345 / 1345.

#107 — 64 % of the mutants came from a single file.

Symptom: "mutation coverage over 14 files" — but proof_check.zig holds 266 of the 420 sites, so a uniform sample put ~25 mutants in one file and 0–1 in the others. Fix: stratified sampling with a guaranteed minimum per file, a fixed recorded seed, and the site distribution published in the defect entry.

#116 — the harness rollback silently discarded an edit made during a run.

Symptom: a README edit vanished, and the file stayed syntactically valid, so nothing looked broken. Found by comparing content, not exit codes: the can-fail harness restores patched files from a byte snapshot taken at the start of each case — and for files the case itself patched, a third-party edit in between was overwritten without a word. Fix: the harness records the hash of what it wrote and refuses to restore when the file changed afterwards; per-case state is reset. Verified by a targeted 3/3 test.
