# KERN Terminology Standard v0.1

> ⚠️ **HISTORICAL (v0.1).** Нормативная терминология раннего этапа. Фраза
> «компилятор ещё не реализован» относится к тому времени; KERN реализован
> (v2.5.1). Документ сохранён как история терминологии.

**Статус:** проект нормативной терминологии для проектируемых KERN / `kernc` / `.kbin`.
**Важно:** это спецификация терминов, а не заявление о том, что компилятор KERN уже реализован.

## 1. Правило единой терминологии

Один термин должен обозначать одну сущность. Разные понятия не должны иметь один общий статус. В языке, машинной схеме, CLI, логах и отчётах используются одинаковые канонические имена.

- Канонические имена сущностей и полей — английские `snake_case`.
- Документация человеку — на русском, с каноническим термином в скобках при первом употреблении.
- Идентификаторы объектов стабильны и не должны зависеть только от отображаемого имени.
- Синонимы разрешены только на уровне пользовательского интерфейса; в машинном ядре они нормализуются к каноническому термину.
- Неизвестное значение, отрицательный результат и ошибка выполнения — разные состояния.

## 2. Объекты предметной модели (ontology)

| Канонический термин | Русское имя | Строгое значение |
|---|---|---|
| `workspace` | рабочая область | Каталог/набор репозиториев, в границах которого идёт исследование. |
| `project` | проект | Логически идентифицируемая система, исследуемая как целое. |
| `corpus` | корпус | Полный набор источников, включённых в конкретный запуск анализа. |
| `artifact` | артефакт | Любой обнаруженный объект: файл, БД, бинарник, лог, набор данных или URL-источник. |
| `artifact_revision` | версия артефакта | Артефакт в конкретном состоянии, описанный хешем/версией/снимком. |
| `source_location` | координата источника | Путь, диапазон строк/байтов, JSON Pointer, ячейка notebook или иной адрес внутри источника. |
| `symbol` | символ | Функция, класс, метод, тип, переменная, константа, theorem или другой именованный элемент. |
| `module` | модуль | Логическая/техническая единица кода или подсистема. |
| `claim` | утверждение | Атомарное, проверяемое высказывание о проекте. |
| `evidence` | свидетельство | Первичный или производный материал, использованный для оценки утверждения. Само свидетельство не равно истинности утверждения. |
| `observation` | наблюдение | Непосредственно зафиксированный результат чтения, измерения или инструмента. |
| `verification` | проверка | Описанная процедура сравнения утверждения с требуемыми критериями. |
| `verdict` | вердикт | Итог проверки утверждения по определённому правилу. |
| `execution` | выполнение | Конкретный запуск команды, теста, сборки, proof checker или эксперимента. |
| `experiment` | эксперимент | Контролируемая процедура с вопросом/гипотезой, условиями, входными данными и результатом. |
| `proof` | доказательство | Формальное доказательство либо ссылка на proof artifact, проверенный указанным доверенным ядром. |
| `metric` | метрика | Числовое/категориальное измерение с определением, единицей и методикой. |
| `relation` | отношение | Типизированная направленная связь двух сущностей. |
| `provenance` | происхождение | Запись о том, откуда объект/утверждение взялось и какими преобразованиями получено. |
| `decision_record` | запись решения | Вопрос, известные факты, варианты, критерии, выбор, причины, последствия и условия пересмотра. |
| `issue` | проблема | Обнаруженный дефект, риск или несоответствие. |
| `blocker` | блокирующее препятствие | Условие, которое не позволяет завершить конкретную задачу/проверку. |
| `open_question` | открытый вопрос | Существенный вопрос, не разрешённый текущими доказательствами. |
| `snapshot` | снимок | Неизменяемое логическое состояние корпуса и индекса в момент времени. |
| `delta` | изменение | Набор добавлений, удалений и изменений между двумя снимками. |
| `agent_task` | задача агента | Ограниченная задача с входами, разрешениями и критериями приёмки. |
| `agent_packet` | пакет передачи | Компактный машиночитаемый контекст, которым один агент передаёт работу другому. |
| `capability` | возможность | Подтверждённая или заявленная возможность инструмента/модели, с отдельным статусом проверки. |
| `tool` | инструмент | Внешняя программа/API/проверяющий механизм, который может быть вызван системой. |
| `trace` | трасса | Упорядоченная запись связанных событий/вызовов для восстановления выполнения. |
| `cache_entry` | запись кэша | Результат вычисления, привязанный к входным отпечаткам, версии метода и происхождению. |
| `diagnostic` | диагностика | Машинная запись ошибки, предупреждения, пропуска или ограничения. |

## 3. Ключевые различия, которые запрещено смешивать

1. `claim` — что утверждается; `evidence` — чем это обосновывают; `verdict` — что решила заданная процедура проверки.
2. `observation` — что инструмент непосредственно сообщил; интерпретация наблюдения хранится отдельно.
3. `execution` — запись запуска; `execution_result` — его выход и статус; наличие исходного кода не доказывает запуска.
4. `proof` — формальное доказательство; `test` — конечная проверка; `benchmark` — измерение; они не взаимозаменяемы.
5. `verified` не означает `proven` во всех смыслах: всегда сохраняется `verification_method` и область утверждения.
6. `unknown` не означает `false`; `not_found` означает только «не найдено в данном корпусе/процедуре».
7. `error` — сбой механизма; `failed` — проверяемая операция завершилась неуспешно; `blocked` — операция не могла быть выполнена.
8. `semantic_similarity` — сходство; `same_meaning` — более сильная гипотеза и без отдельной проверки не устанавливается.
9. `model_assertion` — вывод модели; он не является независимым доказательством сам по себе.
10. `snapshot` — зафиксированное состояние; `cache` — производный ускоритель и не является источником истины.

## 4. Вердикты и состояния

### 4.1 Вердикт утверждения (`claim_verdict`)

- `supported` — критерии поддержки выполнены в указанной области.
- `refuted` — применённая процедура получила достаточное опровержение.
- `unresolved` — данных/проверки недостаточно.
- `conflicted` — есть несовместимые свидетельства и конфликт не разрешён.
- `out_of_scope` — утверждение не относится к текущему корпусу или политике проверки.

### 4.2 Состояние проверки (`verification_status`)

- `planned`
- `running`
- `passed`
- `failed`
- `blocked`
- `cancelled`
- `not_run`

### 4.3 Состояние артефакта/индекса (`artifact_state`)

- `discovered`
- `readable`
- `parsed`
- `indexed`
- `unsupported`
- `unreadable`
- `excluded`
- `stale`
- `missing`

### 4.4 `e=1`

`e=1` — двоичный флаг допуска конкретного утверждения после прохождения его обязательных критериев. Он вычисляется системой по типизированной политике, а не назначается автором KERN или языковой моделью. Для непроверенного/конфликтного утверждения `e=0`. Этот флаг не означает всеобщую философскую истину; действует в границах объявленного корпуса, метода и предпосылок.

## 5. Этапы конвейера (`pipeline_stage`)

Канонический конвейер:

1. `discover` — обнаружить корни и источники.
2. `scope` — зафиксировать границы исследования и исключения.
3. `inventory` — перечислить артефакты.
4. `fingerprint` — вычислить отпечатки источников.
5. `extract` — извлечь исходное содержимое подходящим адаптером.
6. `parse` — разобрать формат в структуру.
7. `normalize` — привести структуру к каноническому представлению без потери исходника.
8. `resolve` — разрешить идентификаторы и ссылки.
9. `link` — построить типизированные связи.
10. `index` — создать поисковые индексы.
11. `verify` — выполнить назначенные проверки.
12. `snapshot` — зафиксировать состояние.
13. `diff` — сравнить два состояния.
14. `query` — выполнить поиск/обход графа.
15. `export` — сформировать отчёты и сериализации.
16. `handoff` — передать задачу другому агенту.
17. `replay` — повторить выполнение из сохранённых входов.

`compile` зарезервирован для преобразования исходного `.kern` в каноническую промежуточную модель и проверки его семантики; `build` — оркестрация требуемых этапов.

## 6. Кэш и воспроизводимость

| Термин | Определение |
|---|---|
| `input_fingerprint` | Отпечаток всех значимых входов операции, включая хеши источников и параметры. |
| `cache_key` | Детерминированный ключ из входного отпечатка, версии алгоритма/модели/схемы и режима. |
| `cache_hit` | Найдена запись с полностью совпавшим ключом и действительными зависимостями. |
| `cache_miss` | Валидной записи для ключа нет. |
| `cache_invalidation` | Запись признана непригодной из-за изменения входов/версии/зависимостей. |
| `replay` | Повтор операции из зафиксированных входов и параметров. |
| `reproducible` | Повтор достиг сопоставимого результата по заранее определённым правилам. |
| `stale` | Производный результат ссылается на устаревший вход или метод. |

Кэш не должен быть источником истины. Ключ для ответа ИИ обязан включать как минимум модель/версию, режим, шаблон инструкции, хеши контекста, схемы вывода и используемых инструментов. Если модель не сообщает версию или параметры, это отмечается как неизвестное.

## 7. Термины вызовов ИИ

- `model_profile` — обнаруженные метаданные модели.
- `model_assertion` — утверждение, сформированное моделью.
- `model_request` — входной запрос к модели.
- `model_response` — ответ модели.
- `tool_call` — структурированный запрос на вызов инструмента.
- `tool_result` — фактический ответ инструмента.
- `agent_trace` — связь request, tool call, tool result, response и затронутых артефактов.
- `context_bundle` — минимально достаточная подборка фрагментов и источников для одной задачи.
- `token_usage` — измеренный/заявленный платформой расход токенов с указанием источника измерения.

## 8. Именование

- Типы/enum: `PascalCase` в Zig, например `ClaimVerdict`.
- Функции/поля: `snake_case`, например `verify_claim`.
- Команды CLI: глаголы в нижнем регистре (`scan`, `build`, `verify`, `diff`, `trace`, `packet`).
- Типизированные идентификаторы: `claim:...`, `artifact:...`, `run:...`, `proof:...`.
- Файлы: исходный `.kern`, двоичный snapshot `.kbin`, SQLite-каталог `.kdb`, переносимый пакет `.kpack` (название временное до фиксации спецификации).
- Не переиспользовать ID удалённого объекта для другого объекта.

## 9. Обязательные поля происхождения

Любая производная запись должна содержать, насколько применимо:

- `id`
- `kind`
- `source_refs[]`
- `source_hashes[]`
- `method_id`
- `method_version`
- `run_id`
- `created_at`
- `status`
- `limitations[]`

Отсутствующее поле не заполняется выдуманным значением; оно получает `null`/`unknown` в соответствии со схемой.

## 10. Политика изменений терминологии

- Термины v0.1 считаются каноническими для первых реализаций.
- Изменение определения требует увеличения версии словаря.
- Переименование поля оформляется как миграция схемы; старые имена могут поддерживаться как входные алиасы, но не должны попадать в канонический экспорт.
- Парсер обязан сообщать неизвестные термины, а не тихо переинтерпретировать их.
- Машиночитаемый словарь должен храниться рядом со спецификацией и участвовать в тестах компилятора.
