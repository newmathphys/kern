## Что подтверждено живым компилятором (не только KERN)

```
# 1
gcc -fsanitize=undefined rot.c && ./rot
rot.c:4:26: runtime error: shift exponent 64 is too large for 64-bit type 'long unsigned int'

# 2
gcc -fsanitize=undefined bs2.c && ./bs2
bs_fn.c:5:26: runtime error: signed integer overflow: 2147483647 - -2147483648
              cannot be represented in type 'int'
```

Оба случая — граница домена: внутренние вызовы в репозиториях безопасны, UB достижим
через публичный API. Это указано в тексте заявок прямо, без преувеличения.

### `tidwall/hashmap.c` #50 — ВОПРОС О ДОСТИЖИМОСТИ
Тидволл спросил прямо: «Does this actually happen? Is `XXH_rotl64` ever called with `r == 0 || r > 63`?

**Ответ (мой, честный): нет, не происходит.** Проверены все 12 вызовов в файле — везде литерал
в [1, 31]. Живого краша нет, и выдумывать его я не стал. Отчёт был про ЛАТЕНТНУЮ UB в `static`-
помощнике без документированного домена. Предложил закрыть как «not a bug», если домен считается
очевидным.

### ПРАВИЛО, КОТОРОЕ Я НАРУШИЛ (записано, чтобы не повторялось)
Отчёт в апстрим ОБЯЗАН начинаться со статуса достижимости:
  1) «достижимо на текущем коде, вот вход» — сильная заявка;
  2) «латентно: в текущем коде не достижимо, вот почему это всё равно важно» — слабая заявка,
     и она должна быть ПЕРВОЙ строкой, а не абзацем в середине.
У меня это было в середине текста, поэтому мейнтейнер справедливо спросил «а бывает ли это вообще».
Вывод: не прятать ограничение в тело заявки — читатель видит первые две строки.

когда нарушение воспроизводится **публичным вызовом на нормальном входе**, а `--xray` без закона
остаётся подсказкой о предусловии (см. `docs/ПАСПОРТ_ВОЗМОЖНОСТЕЙ.md`, раздел «Граница режима»).
