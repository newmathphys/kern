# Двухуровневая индукция: план (НЕ реализовано — названная граница)

## Зачем
Внешний цикл, чей инвариант зависит от переменной, которую меняет ВНУТРЕННИЙ цикл
(`count_primes`: внутренний `for` делает `count -= 1`, внешний инвариант `count >= 0`).
Сейчас это честный SKIP: «вложенный цикл меняет переменные контракта».

## Почему это не патч на 20 строк
Нынешняя модель состояния — ПОДСТАНОВКА (`_apply`: `x -> выражение`). Эффект
внутреннего ЦИКЛА выражением не записывается: он зависит от числа итераций.
Нужен переход к состояниям-ОГРАНИЧЕНИЯМ.

## Звукая схема (Гоар, два уровня)
1. Внутренний цикл ОБЯЗАН иметь свою аннотацию `# @kern:invariant <inv_in>`.
2. Обязательства внутреннего цикла проверяются при предусловии
   `requires_outer ∧ inv_outer`.
3. После внутреннего цикла известно `inv_in ∧ ¬guard_in`: переменные, которые он
   трогал, заменяются СВЕЖИМИ символами `v#in`, а `inv_in` добавляется в ПОСЫЛКИ
   внешних обязательств.
4. Внешний инвариант должен следовать из `inv_in`; иначе FAIL с контрпримером.

## Точки правки
  tools/kern_contracts.py
   * `_assign_paths` (~11135): читать аннотацию внутреннего цикла, собирать
     `inv_in`, заменять трогаемые имена на `v#in`.
   * `check_loop` (~11238): `inv_in` добавить в `pre`.
   * снять ранний `return` для случая «аннотация есть».
   * `_directives_before`: читать аннотацию перед строкой ЦИКЛА, а не только перед `def`.

## Двусторонний контроль (обязателен ДО включения)
  nested_ok            внутренний цикл вне контракта        -> PROVEN (есть)
  nested_bad           меняет контракт, БЕЗ аннотации       -> SKIP (есть)
  nested_annotated     меняет контракт, inv_in есть, следует -> PROVEN
  nested_annotated_bad inv_in есть, НЕ следует              -> FAIL с контрпримером
Без последней пары включать нельзя: сегодня уже был случай (#614), когда первая
версия объявила PROVEN незвучно — поймал контроль.

## Оценка
~150–200 строк, затрагивает ядро модели состояний. Отдельная сессия.
