# Анатомия доказательства: как KERN работает под микроскопом

Экскурсия без чёрного ящика: **что подаём на вход**, **в какое уравнение это превращается**,
**как решатель находит взлом**, **как пруф-чекер проверяет доказательство**. Все выводы ниже —
дословные, снятые с инструмента.

---

## Часть 0. Два режима — и их нельзя путать

| | **Режим 1: Доказательный** | **Режим 2: Обзорный (`--xray`)** |
|:--|:--|:--|
| Что на входе | функция **+ закон** (`@kern:requires` / `@kern:ensures`) | функция **без закона** |
| Что известно о входах | точные границы из закона | только объявленный **тип** (`int` = ±2³¹) |
| Что делает | переводит в уравнение, ищет **доказательство или нарушение** | перебирает **экстремумы типа** (`INT_MIN`) |
| Вердикт | `ДОКАЗАНО` / `КОНТРАКТ НАРУШЕН` + контрпример | «**возможно** переполнение» + контрпример |
| Это баг репозитория? | **да** (закон нарушен) | **нет** — «**подсказка о скрытом предусловии**» |
| Точность | 100% в рамках закона | подсказка, нужна проверка человеком |

**Вывод, который дорого дался:** `--xray` без закона — не «поиск 0-day в чужом коде», а
**подсказчик**: «этой функции для безопасности нужно условие `1 <= r <= 63`». Писать по такой
подсказке в чужой репозиторий — ошибка (Часть 4).

## Часть 1. Закон + код → вердикт

```python
# @kern:requires 0 <= low and low <= high
# @kern:ensures  low <= result and result <= high
def midpoint(low: int, high: int) -> int:
    return low + (high - low) // 2
```

```
python3 tools/kern_contracts.py examples/anatomy/law_ok.py

  [PASS] midpoint: ДОКАЗАНО
ИТОГО: доказано 1 | нарушено 0 | НЕ РЕШЕНО 0 | ЛОЖНЫХ ТРЕВОГ 0
```

## Часть 2. Вот то самое уравнение (реальный файл, 8 строк)

`--emit-smt2` сохраняет уравнение на диск. Полное содержимое `law_ok_midpoint.smt2`:

```lisp
(set-logic ALL)
(declare-const low Int)
(declare-const high Int)
(declare-const result Int)
(assert (and (<= 0 low) (<= low high)))                  ; ЗАКОН: что допустимо на входе
(assert (= result (+ low (div (- high low) 2))))         ; КОД: что делает функция
(assert (not (and (<= low result) (<= result high))))    ; ОТРИЦАНИЕ: «пусть закон нарушен»
(check-sat)
```

По-русски:

1. `low`, `high`, `result` — **символы**, то есть «любые числа», а не один пример.
2. Строка 5 — **закон**: `0 <= low` и `low <= high`.
3. Строка 6 — **тело функции** как равенство.
4. Строка 7 — **отрицание закона**: «предположим, результат вышел за `[low, high]`».
5. `(check-sat)` — вопрос: **существуют ли такие числа?**

Дальше решает математика, а не перебор: `unsat` — таких чисел **нет** (закон всегда выполняется);
`sat` — решатель выдаёт **конкретные числа**, где закон ломается (контрпример).

## Часть 3. Как выглядит взлом: закон нарушен

Код, который возвращает на единицу больше, чем разрешено законом:

```python
# @kern:requires 0 <= low and low <= high
# @kern:ensures  low <= result and result <= high
def midpoint(low: int, high: int) -> int:
    return high + 1
```

```
  [FAIL] midpoint: КОНТРАКТ НАРУШЕН
         [КОНТРПРИМЕР] low = 0, result = 1, high = 0
         [RUNTIME CONFIRMED] нарушение подтверждено и в рантайме (0% ложных срабатываний)
```

Две важные детали:

1. Решатель выдал **не «где-то проблема»**, а точные числа: `low = 0, high = 0`.
2. KERN **не поверил решателю на слово**: подставил эти числа в живую функцию и получил `1` там,
   где закон требует `0`. Отсюда `[RUNTIME CONFIRMED]` — это факт запуска, а не теория.

## Часть 4. Почему `--xray` без закона — только подсказчик

Та же задача на **C** и **без закона** (известен только тип `int`):

```c
int midpoint(int low, int high) {
    return (low + high) / 2;      /* классическая ошибка переполнения */
}
```

```
python3 tools/kern_contracts.py --xray examples/anatomy/midpoint_bug.c

  [OVERFLOW PATH] midpoint: переполнение типа `i32` ([-2147483648, 2147483647])
                  в `low + high` — UB до возврата;
                  [КОНТРПРИМЕР] high = -2147483648, low = ...
```

Инструмент **честно сказал, что знает**: тип `i32` и выражение `low + high`. Он **не знает**, что
настоящий домен — `0 <= low <= high`, поэтому его контрпример начинается с **отрицательного** числа.

Теперь **исправленная** формула `low + (high - low) / 2`:

```
  [OVERFLOW PATH] midpoint_fixed: переполнение типа `i32` в `high - low` — UB до возврата
```

Та же «тревога», хотя формула эталонная. **Причина одна:** без закона `high >= low` инструмент
обязан рассмотреть `high = INT_MIN, low = INT_MAX`, где `high - low` переполняется.

**Урок (стоил одной закрытой заявки в чужой репозиторий):** пока закон не задан, `--xray` — это
подсказка о предусловии, а не баг. Как только закон задан, вопрос решается математически.

## Часть 5. Проверка доказательства пруф-чекером (не «верим Z3»)

Z3 можно принимать на слово, а можно **проверить шаги**. Это делает `kernc`:

```
./zig-out/bin/kernc prove /tmp/smt/law_ok_midpoint.smt2

[L4] SMT-доказательство: /tmp/smt/law_ok_midpoint.smt2
  KERN-EQ2 : T
  e        : 1
  ВЕРДИКТ  : ДОКАЗАНО (допущено)
  [ПРУФ-ЧЕКЕР] шагов 58 | посылок 3/4 | mp 8 | резолюция 3 | Фаркаш 0 | rewrite(лин.) 9
  [PROOF PARTIAL] steps: 58 | premises bound: 3/4 | ... | НЕ ПОД...
```

**Читаем честно:** вердикт `ДОКАЗАНО`, но пруф-чекер пишет `PROOF PARTIAL` и «посылок 3/4» —
часть шагов проверена полностью, часть нет. KERN это **не скрывает**: строка `[PROOF PARTIAL]`
стоит рядом с вердиктом. Когда проверяются все шаги, там будет `trusted: 0, holes: 0`.

## Итог: что считается результатом

| Вопрос | Закон есть | Закона нет (`--xray`) |
|:--|:--|:--|
| «Функция делает обещанное?» | **доказано / нарушено + контрпример** | не спрашивается |
| «Где может упасть?» | контрпример + подтверждение запуском | «возможно, нужно предусловие» |
| «Писать в чужой репозиторий?» | да, если нарушен **публичный** закон | **нет**, только своя заметка |

**Правило проекта:** `--xray` — микроскоп для **своего** кода и для поиска **скрытых предусловий**.
Апстрим-заявка возможна только тогда, когда нарушение воспроизводится **публичным вызовом на
нормальном входе** (пример: `prime_sieve(10)` роняет кучу под ASan).

## Случай 2. `(l+r)/2` падает, `l+(r-l)/2` — нет (живой UBSan)

```
ШАГ 3 — ВЗЛОМ [F]: живой UBSan при l = r = 1073741824
    вариант A: ПАДЕНИЕ — mid_a.c:2:35: runtime error: signed integer overflow: 1073741824 ...
    вариант B: чисто
```

Один и тот же закон `0 <= l <= r`, **два разных ответа** — различие только в формуле.

**ШАГ 2** — уравнение, построенное KERN (`.smt2`):

```lisp
(set-logic ALL)
(declare-const low Int)
(declare-const high Int)
(declare-const result Int)
(assert (and (<= 0 low) (<= low high)))
(assert (= result (+ low (div (- high low) 2))))
(assert (not (and (<= low result) (<= result high))))
(check-sat)
```

**ШАГ 4 [T]** — вердикт и пруф-чекер:

```
[PASS] midpoint: ДОКАЗАНО
ВЕРДИКТ  : ДОКАЗАНО (допущено)
  [ПРУФ-ЧЕКЕР] шагов 58 | посылок 3/4 | mp 8 | резолюция 3 | Фаркаш 0 | rewrite(лин.) 9
  [PROOF PARTIAL] steps: 58 | premises bound: 3/4 | ... | НЕ ПОДТВЕРЖДЕН
```

`PROOF PARTIAL` стоит **рядом** с `ДОКАЗАНО` — часть шагов не подтверждена пруф-чекером, и это
напечатано, а не спрятано.

> **ПОЧЕМУ `PARTIAL` — ИЗМЕРЕНО (не догадка).** Однажды было выдвинуто объяснение: «чекер требует,
> чтобы Z3 использовал ВСЕ посылки файла, а `midpoint` доказывается без `low >= 0`, поэтому `3/4`
> и штраф». Это **неверно**, и вот счётчики того же прогона (`KERN_DEBUG_TRUSTED=1`):
>
> ```
> [dbg-counters] steps=58 holes=0 prem=3/4 unbound=0 mp_bad=0 unitres_bad=0
>                farkas_bad=0 rewrite_bad=0 unknown_rules=0 trusted=12 concl_false=true
> ```
>
> `unbound=0` — **все** посылки привязаны, требование `premises_unbound == 0` выполнено.
> `premises_bound` — это число посылок, реально привязанных к клаузам файла, и оно не обязано
> равняться числу `assert` в файле: неиспользованный `assert` ничего не нарушает.
> Мешает другое — **`trusted=12`**: двенадцать шагов `th-lemma arith` чекер не проверяет
> структурно. Пока в выводе есть хоть один такой шаг, метка `[PROOF VERIFIED]` не печатается
> (`trusted_steps == 0` — обязательное условие, дефект #372: раньше метка выходила при 5 и 2 970
> доверенных шагах). Единственный честный путь к `trusted: 0` здесь — научить чекер проверять
> `th-lemma`, а не ослабить условие.

## Случай 7. QF_AX: теория массивов Маккарти на Си

Закон берётся из `tests/fixtures/project_spec_multi/KERN.md` — директивой `array`:

```
### ring.c :: array_write_hit
- array: buf
```

Функция на Си: `buf[idx] = val; return buf[idx];`

```
[T] ДОКАЗАНО: ring.c :: array_write_hit — steps: 6 | premises bound: 2/2 | mp: 1 | rewrite (linear): 1
  [T] ДОКАЗАНО: money.py :: withdraw — доказано
ИТОГ: T 2 | F 0 | B 0 | N(в законе) 0 | не описано 0
ЗАКОН ПРОЕКТА ВЫПОЛНЕН: все законы доказаны, все функции описаны
```

**ШАГ 2** — то уравнение, что построен для этой функции (реальный файл
`audits/smt2/ring_slot_array_write_hit.smt2`):

```lisp
(set-logic ALL)
(declare-const buf (Array Int Int))                      ; МАССИВ — не отдельные числа
(declare-const idx Int)
(declare-const val Int)
(declare-const result Int)
(assert (and (>= idx -2147483648) (<= idx 2147483647)))  ; тип int32
(assert (and (>= val -2147483648) (<= val 2147483647)))
(assert (>= idx 0))                                      ; закон: индекс неотрицателен
(assert (= result (select (store buf idx val) idx)))      ; КОД: записали и прочитали
(assert (not (= result val)))                             ; ОТРИЦАНИЕ: «прочиталось не то»
(check-sat)
```

Здесь работает **теория массивов Маккарти**, а не перебор индексов: `(store buf idx val)` — новая
версия массива, `(select … idx)` — чтение. Аксиома `select(store(a,i,v),i) = v` даёт `unsat`.

**ШАГ 3-4** — граница видна на трёх файлах:

```
row 1 Маккарти: записанное по idx читается обратно:
  ВЕРДИКТ  : ДОКАЗАНО (допущено)
изоляция БЕЗ гарда (write_idx != read_idx не задан):
  ВЕРДИКТ  : ОПРОВЕРГНУТО (найден контрпример / sat, Белнап F)

изоляция при write_idx != read_idx:
  ВЕРДИКТ  : ДОКАЗАНО (допущено)
  [ПРУФ-ЧЕКЕР] шагов 16 | посылок 3/3 | mp 5 | резолюция 1 | Фаркаш 0 | rewrite(лин.) 4
  [PROOF VERIFIED] steps: 16 | premises bound: 3/3 | mp: 5 | rewrite (linear): 4 | farkas: 0 | trusted: 0 | holes: 0
```

**Вот та строка, ради которой всё делалось:** `trusted: 0 | holes: 0` — **каждый** шаг проверен
пруф-чекером, ни одного доверенного. И рядом честный `НЕ доказано` там, где гарда нет.

**Что доказывает эта таблица:** KERN не «угадывает по коду». Он берёт **закон**, строит уравнение,
и дальше либо **находит число**, которое ломает код (и живой компилятор это подтверждает), либо
**доказывает**, что такого числа нет. Разница между «безопасно» и «возможно» — это разница между
законом и его отсутствием.
