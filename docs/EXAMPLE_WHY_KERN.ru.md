# Зачем KERN: один живой пример, 30 секунд

Эта страница показывает весь смысл KERN на **чужом коде**. Здесь нет
макетов: каждая команда воспроизводима, каждое число измерено.

## Код (не наш)

`TheAlgorithms/C` (22.5k ★), файл `math/lcm.c`, строка 20 — **вербатим**:

```c
int gcd(int a, int b) {
    if (a == 0) return b;
    return gcd(b % a, a);
}

int lcm(int a, int b) { return (a * b) / gcd(a, b); }
```

`lcm` учат как `a*b / gcd(a,b)`. Это верно **математически** и неверно **в
`int`** — но в файле об этом не сказано ни слова, и ни один тест репозитория
не покрывает большие входы.

## Контракт (одна строка намерения)

Их код мы **не трогаем**. Добавляем два комментария над выражением:

```c
/* SOURCE: TheAlgorithms/C @ math/lcm.c, строка 20 — выражение ВЕРБАТИМ:
       int lcm(int a, int b) { return (a * b) / gcd(a, b); }
   Здесь проверяется ЧИСЛИТЕЛЬ `a * b` (i32) — то, что KERN умеет.
   Вызов gcd(a,b) — межпроцедурный барьер, о нём отдельно. */
// @kern:requires a >= 0 and b >= 0
// @kern:ensures result >= a
int lcm_numerator(int a, int b) { return a * b; }
```

## Ответ KERN

```
$ python3 tools/kern_contracts.py lcm_core.c
  [FAIL] lcm_numerator: КОНТРАКТ НАРУШЕН
         [КОНТРПРИМЕР] a = #x643b3fbb, b = #x5a724dfe, result = #x643a7a8a
```

`a = 1681908667`, `b = 1517634558` — и произведение не влезает в `i32`.

## Наземная правда: настоящий компилятор

Контрпример — не бумажное утверждение. Их собственная функция, `gcc`:

```
$ gcc -O0 -fsanitize=undefined -fno-sanitize-recover=all -o lcm_probe lcm_probe.c
$ ./lcm_probe
lcm_probe.c:24:16: runtime error: signed integer overflow:
    1681908667 * 1517634558 cannot be represented in type 'int'
```

**Дефект реальный, и он в коде, который читали миллионы.**

## Что только что произошло, одной строкой

| | |
|:--|:--|
| Тесты | проверяют несколько входов → `lcm(2,3)` проходит → «зелено» |
| **KERN** | проверяет **все** входы `int` → находит точную пару, где ломается |

## Чего KERN здесь **не** делает

- Он **не** читал репозиторий. Ему дали одно выражение и одно правило.
- Он **не** чинил код. Правило написал человек.
- Вызов `gcd` **вне подмножества**, и это сказано честно:
  `SKIP — вне подмножества: узел Call`. Без извлечения арифметического ядра
  `lcm` целиком не проверяется — и KERN об этом говорит, а не догадывается.

## Повторите сами (3 команды)

```bash
git clone --depth 1 https://github.com/TheAlgorithms/C ~/.cache/kern/repos/C
# вставьте файл из раздела «Контракт» выше, затем:
python3 tools/kern_contracts.py lcm_core.c
```

| 8 | **tigerbeetle/tigerbeetle** `src/stdx/stdx.zig` | `divCeil` против `(n + d - 1) / d` | **PROVEN** — 98 шагов, `holes: 0`, сертификат перепроверен собственным пруф-чекером KERN | — |
| 9 | **ghostty-org/ghostty** `src/renderer/size.zig` | `@max(1, cols)` — «сетка никогда не пуста» | **PROVEN** (после дефекта #118: пруф-чекер выучил правила `def-axiom`/`trans*` вместо доверия решателю) | — |
| 10 | **openjdk / Дж. Блох (2006)** | `mid = (low + high) / 2` | **REFUTED** `low = #x00000804, high = #x7ffff7fc, result = #xc0000000` | тот самый девятилетний баг; невидим в `Int`, виден только в QF_BV |

**Шесть репозиториев, пять языков (C, Zig, Rust, Python, Java), десять случаев** —
и два pull-request в upstream. Случай 5 не требует контракта: он сравнивает две
ревизии и показывает смысловое изменение, которое внёс реальный фикс.

**Вердикты надо читать честно.** `PROVEN` — значит обязанность невыполнима, **и**
собственный пруф-чекер KERN перепроверил сертификат Z3. `REFUTED` на **реальных**
(не `…Buggy`) функциях — значит сработала **обязанность безопасности**
(переполнение или нулевой делитель). Это граница применимости, а не обвинение:
KERN говорит «это выражение переполняется на таких входах», а не «ваш проект
сломан». Контроли `…Buggy` существуют потому, что чекер, не умеющий сказать
**нет**, бесполезен.

### Почему случай 4 сформулирован осторожно

Переполнение `result_pow *= n` для возведения в степень **ожидаемо** — честное
утверждение не «вот баг в их коде», а «функция молча заворачивает результат и не
документирует предел; KERN показывает точные входы». Различие важно: ложное
обвинение хуже пропуска.

### Чем эти случаи **не** являются

Ни один из них не CVE, и ни один не найден сканированием репозитория. В каждом
случае правило написал **человек** (или выбрал две ревизии), а KERN решил для
**всех** входов. Измерено на том же конвейере: **0 из 715** функций чужих
репозиториев попадает в подмножество — прогон по репозиторию даёт нули.

## Почему это важно

ИИ-агент (или джун) пишет `lcm` и запускает `lcm(2,3)` — зелено. Та же функция
переполняется на больших входах: молча, в продакшене. KERN — единственная
проверка в цепочке, которая отвечает на вопрос **«верно ли для всех входов»**,
а не «прошли ли эти три примера».

Тот же конвейер нашёл два реальных дефекта в выпущенном коде:

- `TheAlgorithms/C#1595` — `math/catalan.c`: `SIGFPE` при `n = 0` (22.5k ★)
- `TheAlgorithms/C#1596` — `math/lcm.c`: переполнение `a * b` (печатает `-35899` вместо `50000` при `50000,50000`) и `SIGFPE` при `0,0` (22.5k ★)
- `TheAlgorithms/Rust#1075` — `binom(0, 2)`: переполнение `u64` (26k ★)

## Граница, сказанная прямо

KERN — не сканер. Он не найдёт баги в репозитории сам: измерено, **0 из 715**
функций чужих репозиториев попадает в его подмножество. Это **скальпель плюс
турникет**:

- **скальпель** — вы формулируете правило, он решает для **всех** входов;
- **турникет** — не даёт агенту ослабить правило
  (`make contracts-lock-check` → `rc=2`).
