## ФИКС 1: Врата Истины обходились ОДНИМ БАЙТОМ

**Было:** `runTrustedChecker` читал вердикт из `payload[0]`:

```zig
const magic = payload[0];          // <-- байт от ИИ
if (magic == 0xAA) return .Proved; // <-- ИИ управлял вердиктом
```

**Стало:** вердикт формирует ТОЛЬКО `TrustedChecker` (внешний процесс-решатель);
`cert.witness_payload` — это ВХОД для чекера, а не вердикт. Без сконфигурированного
чекера → `.Unknown` → `e=0` (безопасно по умолчанию).

**Доказательство (живой запуск `kern-attack`):**

```
########## АТАКА 1: ИИ присылает ОДИН БАЙТ вместо доказательства ##########
Вердикт: N, e=0
>>> ИТОГ: код НЕ допущен — один байт больше не работает <<<
```

**Тесты:** `ФИКС АТАКИ 1: ОДИН БАЙТ 0xAA больше НЕ даёт e=1` (в admission_gate)
и `ФИКС АТАКИ 1: ОДИН БАЙТ 0xAA НЕ даёт e=1 (уязвимость закрыта)`
(в exhaustive_suite) — оба OK. `runTrustedChecker` удалён.

## ФИКС 2: KERNFS не находил ни одного файла (Фазы 1/3 несовместимы)

**Было:** золотой вектор v1.2 содержал ОДИН объект типа `0x0001` без пути;
пула строк не было; `payload_offset` трактовался как абсолютный.

**Стало:** образ **v1.3** (`tools/golden_v1_3.py`, 410 байт):

- пул строк между таблицей объектов и полезной нагрузкой;
- объект-источник `0x0002` и объект-утверждение `0x0005` — ОБА с путями;
- `payload_offset` и `logical_path_offset` ОТНОСИТЕЛЬНЫ `data_payload_offset`
  (ровно как в спецификации KIMG: «Смещение данных (от data_payload_offset)»,
  «Индекс имени файла в пуле строк»);
- статус Белнапа вынесен в биты 2-3 флагов, чтобы не конфликтовать с
  `HAS_LOGICAL_PATH` (бит 1 из спецификации).

**Доказательство (живой запуск `kern-attack`):**

```

  /raw/src/main.zig -> НАЙДЕНО (22 б): pub fn main() void {}
  /claims/L0_AlignmentInvariant.kern/status -> НАЙДЕНО (view): T
  /claims/L0_AlignmentInvariant.kern/contract.json -> НАЙДЕНО (28 б): {"pre":"true","post":"true"}
  запись -> ошибка: AccessDenied (ожидаем AccessDenied)
>>> ИТОГ: роутер находит объекты — Фазы 1 и 3 согласованы <<<
```

**Тесты:** `ФИКС ФАЗ 1/3: mountFromBytes находит файл и отдаёт zero-copy срез` — OK.

## ФИКС 3: `MerkleRootMismatch` объявлен, но НИКОГДА не возвращался

**Стало:** `KimgHeader.verifyMerkleRoot` пересчитывает корень по таблице
объектов и сверяет с `root_digest`. Единая схема для Python и Zig:

```
leaf_i = SHA256(0x00 || "KIMG-ENTRY-LEAF-V1\0" || entry_bytes_i)
root   = SHA256(0x00 || "KIMG-MERKLE-ROOT-V1\0" || leaf_0 || ... || leaf_{n-1})
```

**Тесты:** `MERKLE: пересчёт корня совпадает и ловит подмену`,
`ФИКС MERKLE: подмена байта в образе ломает монтирование` — OK.

## ФИКС 4: `AccessDenied` объявлен, но возвращался `FileNotFound`

**Стало:** у KERNFS есть явный `write()`, который возвращает `AccessDenied`
(CONF-06). KERNFS — только чтение.

**Тест:** `ФИКС CONF-06: запись в KERNFS отвергается AccessDenied` — OK.

## ФИКС 5: семантика маски `allowed_checkers`

Маска — `1 << checker_id`. Значит `allowed_checkers = 1` разрешает checker 0,
а НЕ 1; для checker 1 нужно `2`. Добавлен `VerificationPolicy.allows()` и тест
`политика: allowed_checkers — битовая маска 1 << checker_id`.

## ФИКС 6: «Fake Witness Rejection» работал не так, как заявлено

Механизм «отвергать свидетели < 8 байт» УДАЛЁН вместе с ошибкой
`FakeWitnessRejected`: это была не защита, а маскировка. Теперь отказ — прямое
следствие того, что без внешнего чекера вердикта нет (тест
`AI-01b: короткий свидетель без внешнего чекера не допускается`).

## ФИКС 8: заворот маски `checker_id` (уязвимость ЕСТЬ И В САМОЙ СПЕКЕ)

**Где:** `VerificationPolicy.allows()`.

**Было (и в спецификации документа, и в нашем коде):**

```zig
const checker_mask = @as(u32, 1) << @as(u5, @truncate(cert.checker_id));
```

`@truncate(checker_id)` (u32 → u5) **заворачивает** индекс: 32 → 0, 64 → 0, …
То есть недоверенный чекер с `checker_id = 32` получал **права чекера 0**.
Если политика разрешала checker 0 — «checker 32» проходил Врата Истины.

**Стало:**

```zig
if (checker_id >= 32) return false;              // fail-closed
const mask = @as(u32, 1) << @as(u5, @intCast(checker_id));
```

**Доказательство:** тест `🔴 ФИКС: checker_id >= 32 НЕ получает прав checker 0`
проверяет `allows(32) = allows(64) = allows(96) = allows(maxInt(u32)) = false`
даже при `allowed_checkers = 0xFFFFFFFF`.

> ВАЖНО: это дефект **самой спецификации**, а не только реализации. KERN
> намеренно СТРОЖЕ спеки: то, что спека пропускает, KERN отвергает.

## ФИКС 9: парсер `.kimg` пропускал 2 обязательные проверки из спецификации

**Где:** `KimgHeader.parse()`.

Спецификация (раздел `src/core/kimg_reader.zig`) требует:

```zig
if (header.major != 1) return KimgError.UnsupportedVersion;
if (header.hash_algo != 1 and header.hash_algo != 2) return KimgError.InvalidHashAlgo;
```

**Было:** поля читались, но **не проверялись**:
* образ иной мажорной версии (другой расклад) разбирался по правилам v1 МОЛЧА;
* образ с произвольным алгоритмом хэша принимался, а диагностика была **ЛОЖНОЙ**
  («Merkle не совпал» вместо «алгоритм не тот»).

**Стало:** обе проверки добавлены; ошибки `UnsupportedVersion` /
`InvalidHashAlgo`; поле 20..24 переименовано `schema_version` → `hash_algo`
(имя из спеки; значения совпадали: 2 = SHA-256).

**Доказательство:** тесты `🔴 СПЕКА: мажорная версия != 1 отвергается` и
`🔴 СПЕКА: hash_algo вне {1,2} отвергается`.

**Побочно найдено:** 18 тестов падали после добавления проверок — их фикстуры
собирали заголовок ВРУЧНУЮ и забывали поля. Введён единый конструктор
`KimgHeader.fillValid()`, исключающий дрейф.

## ФИКС 10: отсутствовал `Eq2.encode(p, n)` из спецификации

Публичный API спеки (16.1.7) содержит `Eq2.encode(pos, neg)` (`code = p | (n<<1)`)
и методы `p()`/`n()`. У нас они отсутствовали (никто не вызывал, но API был
неполон). Добавлены вместе с псевдонимами и тестом полного перебора.

## ФИКС 11: мутационный тестер ПРАВИЛ ИСХОДНИКИ НА МЕСТЕ (затирал правки)

**Где:** `tools/mutate_zig.py`.

**Что было.** Мутатор открывал **оригинальный** файл на запись, вносил мутацию,
запускал тесты и «восстанавливал» исходник из копии, прочитанной ДО мутации.

Последствия (все три реально наблюдались):
1. **Затирание чужих правок.** Правки в `kernfs_router.zig`, сделанные во время
   прогона, были **уничтожены** восстановлением устаревшей копии — два новых
   теста пропали без следа.
2. **Ложные падения.** Параллельный `zig test` (или сборка) видел МУТАНТ вместо
   настоящего кода: тесты «падали» то с `InvalidReservedBytes`, то с
   `FileNotFound`, причём **разным набором** от прогона к прогону. По отдельности
   каждый тест проходил — классическая гонка.
3. **Порча репозитория при аварии.** Если процесс убить во время мутации,
   мутант остаётся в исходниках.

**Стало.**
* мутации вносятся ТОЛЬКО в **копию дерева** (`tempfile.mkdtemp` + `copytree`);
  оригинальные файлы не открываются на запись ни разу;
* файл-замок `.mutation.lock` запрещает параллельные прогоны (в `.gitignore`);
* в начале и в конце считается **sha256 всего `src/`** — если оригинал
  изменился, печатается КРИТИЧНО;
* рабочая копия удаляется в `finally`.

**Доказательство:** прогон печатает
`[i] целостность оригинала подтверждена (sha256 9c96c2006d1d4bda…)`.

## ФИКС 12: ложные «выжившие» мутанты из мутаций ВНУТРИ комментариев

**Где:** `tools/mutate_zig.py`, `collect()`.

Строка `PayloadTampered, // SHA-256(payload) != digest` — мутация `!=` → `==`
применялась к **тексту комментария** и ничего не меняла в поведении, но
попадала в отчёт как «выживший мутант» (ложная «дыра в тестах»).
Теперь перед поиском сайтов мутации отрезается хвост после `//`.

## ФИКС 13: «51 ГБ/с» — это RAW-адресация, а не чтение данных

Полное объяснение и измерения — в `docs/METRICS.md` §4. Кратко:

| Путь | Скорость |
|:--|--:|
| RAW (адресация среза, без проверки) | **76 008 МБ/с** |
| Безопасное чтение (+ сверка SHA-256) | **231 МБ/с** (330× медленнее) |

Введён явный `objectPayloadRaw()` с предупреждением «не проверяет целостность»;
`perf_bench` печатает ОБА числа.
