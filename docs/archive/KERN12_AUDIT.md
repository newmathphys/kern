## 🔴 Ошибки (6)

### 1. Код **не компилируется** как написан

```
src/core/object_entry.zig:46:49: error: expected 1 argument(s), found 0
    var hasher = std.crypto.hash.sha2.Sha256.init();
                                              ^
std/crypto/sha2.zig:103: pub fn init(options: Options) Self
```

В Zig 0.13 `Sha256.init` **требует аргумент**: `Sha256.init(.{})`.
Правка — 4 символа, но без неё `computeLeafHash` не существует.

### 2. 🔴 Тесты из спецификации **не проверяют главную функцию**

```
упоминаний computeLeafHash в файле: 1   (только определение)
вызовов ВНУТРИ тестов:              0
```

Оба теста (`parses safely`, `Reject non-zero reserved bytes`) вызывают только
`parseSafe`. **`computeLeafHash` — ядро Фазы 2 — не вызывается ни разу.**

Именно поэтому `zig test` **напечатал «All 2 tests passed»**, хотя функция
**не компилируется** (ошибка 1): Zig компилирует лишь то, что используется.
Стоило вызвать её из теста — компиляция сразу упала.

**Вывод:** «CONF-10..CONF-15 проверены тестами» — **неверно** для Merkle-части.

### 3. `blake3_hash()` **никогда не использует BLAKE3**

```python
def blake3_hash(data: bytes) -> bytes:
    # В Python используем hashlib.sha256 как фоллбэк, если пакета blake3 нет
    # В реальном prod будет: import blake3; return blake3.blake3(data).digest()
    return hashlib.sha256(data).digest()
```

Никакого `try/except` здесь **нет** — это не «фоллбэк», а **жёстко зашитый
SHA-256**. Комментарий описывает механизм, которого не существует.

Проверка по факту: в заголовке `702330f4e4c8e62b…` — это **SHA-256**;
BLAKE3 от тех же данных дал бы `a5a75ddd9c9306e1…`.

### 4. 🔴 Обещанный «prod-вариант» **ломает** Zig-ядро

Сделал ровно то, что обещает комментарий (`import blake3`):

```
Golden Vector: Root Digest: 28cd22f346219438...
Cross-check: Zig Merkle root == Python golden vector root...
  expected (BLAKE3): 28 CD 22 F3 46 21 94 38 ...
  found    (SHA-256): 80 00 2D D2 5F E7 3D 75 ...
```

**Сквозная сверка ПАДАЕТ.** То есть спецификация говорит «BLAKE3», Python-код
говорит «в prod будет BLAKE3», а Zig-ядро считает **SHA-256**. Выполнение
обещания из комментария **разрушает совместимость**.

**Алгоритм Merkle-корня в v1.2 не определён однозначно.**

### 5. Заявленное «исправление» `reserved` **ничего не меняло**

```
v1.1: <32s Q Q Q I H B B I I 24s
v1.2: <32s Q Q Q I H B B I I 24s
идентичны: True | размер: 96
```

`reserved` был **24 байта уже в v1.1**. «Исправление арифметики в v1.2» —
описание уже сделанного. Формат не изменился.

### 6. 🔴 `payload_offset` сменил смысл — **ломает Фазу 3 молча**

| Версия | Комментарий | Значение |
|:--|:--|:--|
| v1.1 | «**Абсолютное** смещение контента» | абсолютное |
| v1.2 | «`payload_offset` (**от** `data_payload_offset`)» | **относительное** = 0 |

Логика KERNFS из Фазы 3 (`mmap_slice[payload_offset .. +size]`) считает смещение
**абсолютным**. На образе v1.2 она вернёт **заголовок** вместо содержимого:

```
срез [0..56]  = b'KIMG\r\n\x1a\n\x01\x00\x00\x00\x80\x00...'   ← заголовок
должно быть  = b'{"schema": "kern.project-manifest/1", ...}'   ← содержимое
```

**Фаза 3 и v1.2 несовместимы**, и узнаётся это только при чтении данных.

## Моя ошибка в этом аудите

Я предположил, что `blake3_hash` — это «фоллбэк с `try/except`», и что установка
пакета `blake3` переключит Python на BLAKE3. **Проверка показала иное:**
`try/except` в функции **нет вовсе** — она жёстко зашита на SHA-256, поэтому
установка пакета ничего не изменила. Я исправил вывод: проблема не в «фоллбэке»,
а в том, что **комментарий описывает несуществующий механизм**, а «prod-обещание»
из него ломает формат (проверено отдельно).
