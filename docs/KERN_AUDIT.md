## Часть 2. Что делает `kernc` на деле

Запуск на `test_project.kern`:

```
[KERN] L3: claims found: 3
  -> 'MemoryPoolAlignment'    | Belnap: truth
  -> 'AI_Hallucination_Code'  | Belnap: falsity
  -> 'NetworkAuth'            | Belnap: truth
[KERN] L0: binary cache written (project.kbin)
OK: CANONICAL_PROJECT.md
```

### 🔴 `project.kbin` — **0 байт**

Заявлено: *«Бинарный кэш записан (project.kbin, 64-byte aligned)»*.
Факт: **пустой файл**. В `main.zig` файл только создаётся — **ни одной записи**.

Следствие: структура `KbinHeader` (те самые 64 байта, SoA-массивы, `blake3_digest`)
**не используется нигде** — `src/format/kbin_soa.zig` не импортируется ни одним
модулем. Это **мёртвый код**, а не «L0-слой».

### 🔴 «SMT-мост» — это **подстрочный поиск**

```zig
pub fn verifyAntiVacuity(witness: ?[]const u8) BelnapTruth {
    if (witness == null or witness.?.len == 0) return .none;
    if (std.mem.indexOf(u8, witness.?, "unsat") != null) return .falsity;
    if (std.mem.indexOf(u8, witness.?, "model_sat_witness") != null) return .truth;
    return .conflict;
}
```

Никакого SMT-решателя здесь нет. Проверено **ложным доказательством**:

| Утверждение | Свидетель | Вердикт KERN |
|:--|:--|:--|
| `FakeProof` — «абсолютно ничего не доказано» | `это_не_доказательство_но_содержит_model_sat_witness` | **`truth` (ПРОВЕРЕНО)** |
| `Order` | `model_sat_witness_unsat` | **`falsity`** (потому что `unsat` проверяется первым) |

**Достаточно вписать в текст слово `model_sat_witness` — и утверждение
объявляется доказанным.** Порядок проверок влияет на вердикт.

### 🔴 `zig build test` — **0 настоящих тестов**

Заявлено: *«Run KERN Foundation math tests»*. Фактически `build.zig` запускает
тесты **только** из `simd_belnap.zig`, а там единственный тест:

```zig
test "Belnap Logic" {
    try std.testing.expectEqual(1, 1);   // ← проверяет, что 1 == 1
}
```

Команда возвращает **код 0** и **пустой вывод**. Логика Белнапа (планы `t_plane`
и `f_plane`, метод `set`) **не проверяется вообще**.

### Найденное в логике (по коду, компилятор подтвердил сборку)

* Неизвестный свидетель → **`conflict`** (B = «и истина, и ложь»). Это сильное
  утверждение о противоречии, хотя правильнее `none` («неизвестно»).
  Проверено: `witness: "что-то_неизвестное"` → `conflict`.
* Отсутствие свидетеля → `none` (корректно).
* Пустой файл → `0 claims`, и всё равно `OK` (нет сообщения, что разбирать нечего).

## Часть 3. `kern.py`: что работает и что нет

### ✅ Работает (проверено)

| Возможность | Результат |
|:--|:--|
| `snap` | 8 файлов упакованы, бандл 8 262 байта |
| `read` | человекочитаемый отчёт выводится |
| `restore` | **байт-в-байт**: `diff -r` не нашёл различий |
| **Заявление про ZIP** | ✅ **ВЕРНО**: `unzip -l` и Python `zipfile` открывают бандл как ZIP |
| **Обнаружение подмены** | ✅ **РАБОТАЕТ**: подменённый `build.zig` → `КРИТИЧЕСКИЙ СБОЙ`, **код возврата 1** |

### 🔴 ZIP SLIP — запись **вне** каталога назначения

`cmd_restore` делает `os.path.join(dest_dir, name)` **без проверки** `name`.
Бандл с записью `../../ZIPSLLIP_PWNED.txt`:

```
  [OK] ../../ZIPSLLIP_PWNED.txt
[ГОТОВО] Все 1 файлов восстановлены.
```

Файл оказался в **`/tmp/ZIPSLLIP_PWNED.txt`** — **вне** `/tmp/kerntest/slip_out`.

**Последствие:** вредоносный `.kern.bundle` пишет файлы **куда угодно**, куда
может писать пользователь. Это уязвимость, а не мелочь.

### 🔴 Частичная запись при сбое — нет атомарности

При обнаружении подмены `sys.exit(1)` срабатывает **после** записи части файлов:

```
код: 1
что осталось на диске после сбоя:
kern.py
test_project.kern
```

Каталог назначения остаётся в **несогласованном** состоянии: часть файлов есть,
остальных нет, и об этом никто не сообщает.

### 🔴 Необработанный сбой ZIP → трейсбек Python

При повреждении CRC `kern.py` **падает**:

```
zipfile.BadZipFile: Bad CRC-32 for file '.kern_manifest.json'
```

Обещанное «КРИТИЧЕСКИЙ СБОЙ: файл … скомпрометирован» **не появляется** —
исключение летит наружу, потому что `zf.read()` не обёрнут в `try/except`.
Пользователь видит трейсбек вместо понятного сообщения.

### 🔴 «Семантический анализ» — генератор **ложных** срабатываний

Проверка: `re.search(r"(\w+)\s*-\s*(\w+)")` и отсутствие слов `if` / `assert`.

Фактическое срабатывание на тестовом проекте:

```
* src/tools/scanner.zig: Риск целочисленного переполнения (Underflow)
```

Что это было на самом деле:

```
совпадение: 'KERN-D'
контекст: ...writer.print("## KERN-D\n```kern\n", ...
```

**Заголовок Markdown `"KERN-D"` объявлен риском целочисленного переполнения.**
Арифметики в файле нет вовсе.

### 🔴 Память: корпус 600 МБ → **пик RSS 2 171 МБ**

| Метрика | Значение |
|:--|--:|
| Размер корпуса | 600 МБ (2 файла × 300 МБ) |
| **Пик RSS** | **2 171 МБ** — в **3.6 раза** больше корпуса |
| Время | 26.7 с (**22 МБ/с**) |
| Размер бандла | 600.2 МБ |

Причины (по коду):
1. `analyzed_files[rel_path] = content_bytes` — **все файлы держатся в ОЗУ**;
2. `zip_buf = io.BytesIO()` — **весь архив в ОЗУ**;
3. `zip_buf.getvalue()` — **ещё одна копия** того же объёма.

Для проекта на 5 ГБ это ~18 ГБ ОЗУ. **Это и есть та «утечка памяти»**, которую
пользователь замечает: не утечка как таковая, а пик в 3.6× от объёма данных.

### ⚪ Пустой каталог → «Все системы работают стабильно»

```
Файлов в базе: 0
## Сводка: Все системы работают стабильно
Критических противоречий и незащищенных операций не выявлено.
```

Про **пустой** проект сказано, что «всё стабильно». Формально верно, по сути —
пустое утверждение.
