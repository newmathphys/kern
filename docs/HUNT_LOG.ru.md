**Единственное срабатывание и почему оно снято.** `dcddirif.cc:4549`:

```c
if ((pgmWidth > 0) && (pgmHeight > 0) && (pgmWidth <= 0xffffu) && (pgmHeight <= 0xffffu)) {
    const unsigned long pgmSize = pgmWidth * pgmHeight;   // ≤ 65535² = 4 294 836 225 < 2³²
    Uint8 *pgmData = new Uint8[pgmSize];
```

Границы проверены ОБЕ и до умножения, тип `unsigned long` (64-бит на LP64), максимум
произведения помещается даже в 32 бита. Класс `iio` здесь не достигается.

**Что это говорит о детекторе (честная точность на этом срезе):** 1 срабатывание,
0 пригодных. Причина снятия названа: наш гард-фильтр ищет `SIZE_MAX/` и каст, но не
узнаёт парную проверку `(w <= 0xffffu) && (h <= 0xffffu)` на двух множителях. Это
калибровка, которую МОЖНО добавить; до неё такие кандидаты требуют ручного чтения.

**Потолок зафиксирован по правилу остановки:** три проекта, один кандидат, ноль
пригодных. Дальнейшая охота запросами и точечными прогонами **останавливается** до
прихода внешних сигналов (`iio` PR #24, Glama, внешний `receipt.log`).

**КАЛИБРОВКА №22 (парный гард), 2026-11-25.** Детектор узнаёт защиту, когда
ОБА множителя ограничены сверху, знаковый тип имеет и нижнюю границу, а
произведение потолков `max_a * max_b * k_lit * scale` укладывается в 2³¹ (int)
или 2³² (unsigned). Четыре контроля, снятые кодом:

| Контроль | Ожидание | Измерено |
|:--|--:|--:|
| DCMTK-паттерн: `w,h <= 0xffff`, `size = w*h` | 0 | **0** |
| тот же гард, но `w*h*4` (65535²·4 > 2³²) | ≥1 | **1** |
| без гарда, `int size = w*h` | 1 | **1** |
| эталоны `stb_image.h`, `qoi.h`, `dr_wav.h` | 0 | **0** |
| `DCMTK/dcmdata/libsrc` (98 файлов) | 0 | **0** |

Заодно поймана собственная ошибка того же класса, что `#657`/`#661`: неверный
импорт (`_has_safe_left_wide_cast` живёт в `_witness`, а не в `api_hunt`) давал
`ImportError`, который в `analyse_z3_alloc` ловится как `except ImportError: pass`
и **молча отключал всю форму E**. Все три контроля показывали 0 — и это выглядело
как «чисто». Исправлено; проверка «форма E включена» должна быть в селфтесте.

## 14. Новый ствол `round-trip` (`decode(encode(x)) != x`): первые две цели — 0

Метод: сериализовать значение самим проектом, прочитать обратно ЕГО ЖЕ парсером и
сравнить с исходным. Нарушение такого закона почти невозможно закрыть как
«by design», и оно воспроизводится пятью строками без внешних данных.

| Цель | Версия | Проверок | Расхождений | Вердикт |
|:--|:--|--:|--:|:--|
| `httpx` (URL / QueryParams / Headers) | 0.28.1 | 44 | 1 | **by design**: HTTP/1.1 заголовки — ASCII, `Headers({"x": "unié"})` обязан падать (`UnicodeEncodeError`) |
| `PyYAML` (`safe_dump` → `safe_load`) | 6.0.4 | 35 | 1 | **by design**: YAML не имеет кортежа; `(1, 2)` -> `[1, 2]` — известное свойство формата |

Наборы значений, которые ОБЯЗАНЫ были сломаться и не сломались: `"yes"/"no"/"on"/"off"`,
`"null"`, `"1.0"`, `"0x10"`, `"1e3"`, пустая строка, пробел, табуляция, перевод строки,
кавычки, `"a: b"`, `"a #b"`, `"- item"`, юникод, 500 символов, `2**63`,
`-(2**63)-1`, `0.1`, `-0.0`, `inf`, `nan`, пустые `{}`/`[]`, вложенные структуры.

**Вывод по методу:** оба проекта сериализуют честно, включая `-0.0` и `nan`. Это
означает, что ствол работает (расхождения ловятся в принципе), но на этих двух
целях доказывать нечего. Следующие цели того же класса: `pydantic`, `starlette`,
`tomli-w` + `tomllib`, `urllib.parse` (там `+` vs `%20` — исторический источник
несимметричности).

## 15. `pydantic` NaN round-trip: НЕ дефект, осознанный компромисс (проверено до репорта)

Наблюдение (3 строки): `F.model_validate_json(F(f=nan).model_dump_json())` падает, потому
что дефолт `ser_json_inf_nan="null"` пишет `{"f":null}`, а поле `f: float` принимает только
число. Выглядит как нарушение `decode(encode(x)) == x`.

**Проверено ДО любого обращения в трекер (урок `typst#9103`/`gleam#6524`):**

| Проверка | Результат |
|:--|:--|
| трекер `pydantic/pydantic` по `ser_json_inf_nan` | **#10037 open** «`model_dump(mode="json")` can output non-serializable NaN», **#12260 open** «Unions do not respect `ser_json_inf_nan`», **#13996 closed** — тема известна и активно ведётся |
| `ser_json_inf_nan="strings"`, lax | `{"f":"NaN"}` → чтение **OK** (`nan`) — штатный round-trip-режим |
| `ser_json_inf_nan="strings"`, `strict=True` | **падает** `float_type`, потому что strict-режим отключает приведение `str -> float` — это его документированная семантика |
| `bytes(b"\xff\xfe")` | `PydanticSerializationError` — bytes не представимы в JSON |

**Вердикт: НЕ репорт.** `null` — единственное RFC-8259-совместимое представление
нечислового float, выбор сделан осознанно и уже обсуждается в открытых тикетах;
`strings` — документированный обход для round-trip, а его поведение в `strict=True`
следует из определения strict. Отправка была бы четвёртым «закрыто как задумано».

**Что осталось верным измерением:** `-0.0`, `2**63`, `-(2**63)-1`, `Decimal("1E+3")`,
`Decimal("1.500")`, `Union[int,bool]` (`1` -> `1`, `True` -> `true`), `Literal[1, True]`,
`datetime` наивный и `+00:00` — **все прошли round-trip**. TOML (`tomli-w`+`tomllib`,
`tomlkit`) на корпусе `\r`, управляющих символов, `2**63`, `nan`, `inf`, пустых таблиц — **0 расхождений**.

## 16. `kernc --xray` на `libgit2` (2026-11-22): 11 находок, 0 подтверждено, причина названа

`src/` 387 файлов, **2748 функций**, `checked 503 | trivial 1228 | skipped 1017`, **11 находок**.
Для сравнения `libarchive` (176 файлов): 226 функций, `checked 25`, 0 находок.

| Точка | Прочитано | Вердикт | Причина |
|:--|:--:|:--|:--|
| `transports/smart_pkt.c:ok_pkt` | да | **ложное** | нет постусловия `prefixncmp(line,len,"ok ")==0 ⇒ len>=3` |
| `util/tsort.c` `merge` ×2, `collapse` ×3 | да | **ложные** | `else` после исчерпания `d<=1` и трёх ветвей `d==2` ⇒ `d>=3` |
| `util/date.c:git_date_rfc2822_fmt` | да | не дефект | `offset * 60` при `int offset` — переполнение требует `offset > 3.5e7`, вызывающие передают минуты пояса (|offset| ≤ 840); публичный API, контракт «минуты» |
| `cmd_blame.c:fmt_date`, `path_w32.c`, `config_file.c`, `oid.c` | **нет** | не проверялись | вердикт по имени функции не выносился |

**ДЕФЕКТ ТОЧНОСТИ (заведён, не исправлен).** При индексации `a[d - k]` движок не использует
границы, выведенные из `while`-инварианта и исчерпания ветвей: в `collapse` условие
`if (stack_curr <= 1) break;` даёт нижнюю границу, а три ветки `stack_curr == 2`
исчерпывают двойку, поэтому в `else` заведомо `stack_curr >= 3`. Это **interval narrowing
по цепочке if/else**, и его отсутствие даёт ложный `[BOUNDS PATH]` (пункт `#570`:
«индекс не литерал окна»).

Двусторонний тест, который должен появиться вместе с правкой:

```c
/* A: исчерпание — находки быть НЕ ДОЛЖНО */
while (1) { if (d <= 1) break; if (d == 2) { f(); } else { a[d - 3] = 0; } }
/* B: без исчерпания — находка ОБЯЗАНА остаться */
while (1) { if (d <= 1) break; if (d == 5) { f(); } else { a[d - 3] = 0; } }
```

**ПРИЧИНА 5 ЛОЖНЫХ В `tsort.c` НАЙДЕНА И ОКАЗАЛАСЬ НЕ ТОЙ, ЧТО КАЗАЛОСЬ (2026-11-25).**

Проверено чтением, а не догадкой: строка `10647` **уже передаёт** `path_conds +
_clike_conds_at(im.start(), if_blocks, body)` в `_smt_sat_guarded` — тот же приём, что
`_ov_path:9447`. Значит narrowing в границах есть, и «path_conds не пробрасывается» —
**опровергнутая гипотеза** (вторая за окно: первая, `_list_read`, проверена экспериментом
и откачена — фикстуры A и B обе дали 1).

Настоящая причина — **`#522`: `break`/`continue`/`goto` не моделируются как выход из
ветви**. В `collapse` ограничение `d >= 3` складывается из `if (d <= 1) break;` (даёт
`d > 1`) и исчерпания трёх ветвей `d == 2`, а первое звено в модели путей отсутствует
вовсе. На `cmark-gfm/src` это же видно числом: **2130 заметок уровня ветви** с причиной
«`break`/`continue`/`goto` не моделируются».

**Следствие для плана:** правка narrowing НЕ даст `libgit2 11 → 6`. Пять ложных уйдут
только после моделирования выхода из ветви — это работа над CFG (`#522`), а не над
пробросом условий. До неё `libgit2` остаётся: 11 находок, 7 прочитано, 0 подтверждено.

## Отклонён: `zqfang/GSEApy` (722 ★) — паника недостижима, защита на Python-границе

Цепочка в коде существует: `pub compute_density` → `mat_ecdf` → `apply_ecdf` →
`x0.sort_unstable_by(|a, b| a.partial_cmp(b).unwrap())` (`src/gsva.rs:92`), то есть
`NaN` в строке матрицы обязан паниковать. Мейнтейнер в #256 пишет: «so far NaN is
allowed in the input data (this is because of the rust backend)».

**ЖИВОЕ РЕПРО (uv venv, gseapy + pandas):**

```
[WARNING] Input data contains NA, filled NA with 0
ВОЗВРАТ: <gseapy.gsva.GSVA object at 0x…>
```

`gseapy.gsva()` **обнуляет NA на границе Python** и предупреждает об этом — до Rust
`NaN` не доходит, поэтому `unwrap()` недостижим из публичного API. Фраза мейнтейнера
означает именно это, а не «пропускаем NaN внутрь».

**Вердикт: не репорт.** Урок, который дороже кейса: чтение Rust-кода без проверки
Python-обёртки дало ложное «противоречие контракта и кода». Спасла одна команда
живого запуска — четвёртый раз за серию (после pydantic, efl, typst/gleam).
