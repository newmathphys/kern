## 1. Находить логические баги (QuixBugs)

**Заявление:** «KERN ловит 31/31 бага без запуска тестов, доказав невыполнимость».

**Статус: ⚠️ РЕЗУЛЬТАТ верен, СПОСОБ — нет.**

| | |
|:--|:--|
| ✅ Результат | **31/31** багов обнаружено (`tools/quixbugs_full.py`) |
| ❌ Способ | это **НЕ** символьное доказательство |

**Как на самом деле:** баги ловятся **реальным исполнением** официальных
тест-кейсов QuixBugs:
```python
spec = importlib.util.spec_from_file_location(name, path)
spec.loader.exec_module(m)          # загружаем багованный модуль
run_cases(fn, cases, timeout=1.0)   # прогоняем тесты + таймаут (зависания)
```
Это **динамический прогон**, а не Z3-доказательство. Отличие важно:
динамический прогон ловит только те баги, для которых есть тест-кейс.

**Символьное доказательство** применяется в других проверках (§2, §4, §5).

## 3. Быть шлюзом для внешних моделей (Admission Gate)

**Заявление:** «KERN стоит между LLM и продакшеном: непроверенный код → `e=0`».

**Статус: ⚠️ ПОДТВЕРЖДЕНО, но без улучшения pass@1.**

| Метрика | Значение |
|:--|--:|
| Точность блокировок | **100%** (55/55 заблокированных реально падали, **0 ложных**) |
| Полнота (сколько падений найдено) | 70.5% |
| **Влияние на pass@1** | **0** (0.524 → 0.524) |

**Честно:** статический гейт **не поднимает** pass@1 — он срабатывает раньше
тестов. Его ценность — **нулевой уровень ложных срабатываний**: он никогда не
блокирует рабочий код. Чтобы реально отсеивать логические ошибки, нужно
**исполнение** (Execution Runner), а не статический анализ.
