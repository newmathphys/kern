## §1. Четыре открытых вопроса (каждый с числом и командой)

### 1.1 `def-axiom` — новое первое неисправленное правило в `add_three.4_bit` (1020)

**Что известно точно:** до fallback доверенных было 2970 и первым правилом был
`unit-resolution`. После fallback — 1020 и первым стало `def-axiom`. Значит
`unit-resolution` **больше не первый**: остаток держит `def-axiom`.

**Что известно про `def-axiom` в коде:** правило ЕСТЬ в `KNOWN_RULES` и имеет
проверку тавтологичности (`verifyDefAxiom`). Дамп ранее показал форму
`(def-axiom (or $x2688 k!140 $x3214))` — то есть с **skolem-константой** `k!140`.

**Гипотеза (проверить дампом, НЕ верить):** аксиома определения для skolem-константы
НЕ является тавтологией сама по себе — её надо проверять против ОПРЕДЕЛЕНИЯ
`k!140` из вывода (шаг `anchor`/`sk.` или `(let ((k!140 …)))`).

**Команда:** дамп 5 первых `def-axiom` + их раскрытых заключений:
```bash
KERN_DEBUG_TRUSTED=1 ./zig-out/bin/kernc prove ~/.cache/kern/smtlib4/QF_BV/add_three.4_bit.smt2 2>&1 | grep -m 20 'dbg-trusted'
```

### 1.2 `storeinv`: `lemma` ×2 и `monotonicity` ×2 (4 доверенных)

**S-выражения уже сняты дампом** (не нужно снимать заново):
```
#1 lemma :: (lemma (unit-resolution @x184 @x104 false) $x162)
#2 monotonicity :: (monotonicity @x101 (= (select ?x29 i1) ?x108))
#3 lemma :: (lemma (unit-resolution @x184 @x81 false) $x145)
#4 monotonicity :: (monotonicity @x101 (= ?x140 ?x156))
```

**Что видно невооружённым глазом:**
* `monotonicity` здесь — КОНГРУЭНЦИЯ: из `@x101` выводится равенство. В коде есть
  `verifyMonotonicity`, но она не взяла эти две формы (вероятно, `@x101` — ссылка
  на шаг, чьё заключение — равенство термов, а `?x29`/`i1` — нераскрытые имена).
* `lemma` — разрядка гипотез (RAA): поддерево выводит `false`, заключение —
  отрицание гипотез. В коде есть `verifyLemma`; надо понять, ПОЧЕМУ не взяла
  именно эти две формы.

**Команда (нужен дамп ВНУТРЕННЕЙ причины, а не только S-выражения):**
добавить в `verifyMonotonicity`/`verifyLemma` печать ветки отказа под
`KERN_DEBUG_TRUSTED` (по образцу `[dbg-ur-unver]`) и прогнать `storeinv`.

### 1.3 `premises_unbound`: `1/8` на `storeinv` и `0/188` на `add_three`

**Это НЕ то же самое, что доверенные шаги.** `premises_unbound` — непривязка посылок
к КОНТРАКТУ задачи. Именно из-за неё обе задачи печатают
`[!] ПРУФ-ЧЕКЕР ОТВЕРГ вывод решателя`, хотя `дыр 0`.

**Важно:** это отдельная граница. Её нельзя «закрыть» ослаблением — только
разбором: какие именно `(asserted …)` шаги не совпали с контрактом.

**Команда:** в гейте `tools/smtlib_proof_check.py` уже есть разбор причины;
дамп непривязанных посылок — под `KERN_DEBUG_LIA` (`[dbg-unbound]`).

### 1.4 Отчётность: колонка «резолюция» не отражает 1950 проверенных шагов — ✅ ЗАКРЫТО (`#432.1`)

**Измерено:** на `add_three.4_bit` колонка `резолюция` равна `5247` И ДО, И ПОСЛЕ
fallback, хотя доверенных стало на 1950 меньше. Значит колонка считает
**число шагов правила**, а не **число проверенных**.

**Почему это важно:** читатель отчёта не может увидеть, что работа сделана. Это
ровно класс `#428` (число есть, ответа нет).

**СДЕЛАНО (`#432.1`):** счётчики `mp`/`резолюция` считают ПРОВЕРЕННЫЕ шаги; добавлено
поле `other_steps` (asserted/hypothesis/intro-def/без правила) и колонка `прочих N`;
в гейт добавлен ИНВАРИАНТ ТОЖДЕСТВА `проверено + доверенных + прочих + дыр == шагов`
с двусторонней ветвью selftest. **ИНВАРИАНТ СРАЗУ НАШЁЛ `#433`** (см. §1.5).
