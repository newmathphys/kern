**Поправка к тому, что этот файл говорил раньше.** Корзина «нет `if`» была описана
как «честная граница, НЕ потеря (нечего ветвить)». Это верно **лишь наполовину**:
ветвить нечего, но обязанности (переполнение, деление, границы) там **проверяются**,
а счётчик всё равно сообщает эти функции как `skipped`. Это дефект **#405**, и
поэтому существует шаг 2.

**Вторая предпосылка, найденная при перемерке: Z3 обязан быть в `PATH`.** Без него
живое доказательство #405 НЕВИДИМО — `--xray` печатает `находок 0` и ни одного
предупреждения (дефект **#407**). Любой прогон `--xray` в этом проекте —
`PATH="$PWD/.venv/bin:$PATH"`.

Оба корпуса зафиксированы по SHA (`27d942c8`, `0c3a9c33`), поэтому «до/после»
меряется на одних и тех же байтах; клоны лежат в `~/.cache/kern/repos/`.

5. **Гистограмма причин пропуска C-like `--xray` ИЗМЕРЕНА (дефекты #400, #401).**
   Сводка заявляла «skipped N with explicit reasons», не выводя НИ ОДНОЙ;
   теперь причины записываются, нормализуются в структурные ключи, печатаются, и
   сумма сверяется со счётчиком. Измерено: `cmark-gfm/src` 232 пропуска,
   `toolkit/packages` 400 — суммы сходятся. Гейт `tools/xray_skip_reasons_check.py`
   (вызывается из `xray-check`), кейс `xray-skip-reasons`.
6. **Четыре ЛОЖНЫХ `[DEAD BRANCH]` на реальном `cmark-gfm/src/utf8.c` убраны (#401).**
   `if_derived` накапливал `(not cond)` для каждого вышедшего блока без учёта
   ветви, поэтому взаимоисключающие ветви противоречили друг другу
   (`str1 >= 160` И `str1 < 160`) и путь становился UNSAT. `_clike_conds_at` теперь
   учитывает вложенность; `if_derived` удалён. Находок 4 -> 0 при неизменном
   охвате (76/308), а ДЕЙСТВИТЕЛЬНО мёртвое условие по-прежнему находится.
   Кейс `xray-nested-branch`.

## Правила процесса, которые не раз спасали проект

1. **Сверять каждое опубликованное число и команду с кодом**, а не с пересказом.
   Четыре из десяти внешне составленных «доказательств» не совпали с репозиторием.
2. **Никогда не запускать проверку в одной пачке с правкой того, что она проверяет** —
   за одну сессию эта гонка случилась трижды и дала ложный `IndentationError` и
   устаревшие чтения.
3. **Большие новые файлы писать атомарно** (`cat > file <<'EOF'` или один вызов
   редактора). Серия `insert_line` в растущий файл рвала функции пополам.
4. **`zig` в `PATH` может оказаться pip-пакетом `ziglang` 0.13** (он лежит в
   `.venv/bin` намеренно, для `portable-bench`). Ставьте настоящий Zig первым,
   иначе сборка падает ошибкой, обвиняющей наш собственный `build.zig`.
5. **Новый файл с якорями `fact:` обязан быть добавлен в `SURFACES`** — иначе
   страж сирот его отвергает (дефект #246).
6. **Новая CHECK-цель требует canfail-кейса и записи в `CASE_TARGET`**, а новый
   кейс требует файла, который он патчит, в `FAULTABLE`.

## Чего заявлять НЕЛЬЗЯ

- KERN — не сканер: он не ищет баги в чужих репозиториях сам (измерено: 0 из 715
  функций чужих репозиториев попадают в подмножество).
- `[BOUNDS] … длина НЕ известна` — кандидат, а не обвинение.
- SKIP / «вне подмножества» никогда не является доказательством корректности.
- Оракулы ReDoS и non-interference — **измерения с порогами**, а не
  детерминированные доказательства.
