# KERN — РЕЕСТР ОГРАНИЧЕНИЙ (Known Limitations / Defect Catalog)

> Признак зрелой инженерии — **открытое** описание границ применимости.
> Здесь перечислено то, чего KERN **не** делает, и при каких условиях
> результаты могут быть неполными. Ни одна строка не является «отговоркой»:
> у каждого ограничения указано, как его обнаружить.
>
> Формат: DO-330 TQL-1 / ISO 26262 TCL-1 (реестр ограничений инструмента).

## A. Ограничения по методам доказательства

| # | Ограничение | Что это значит | Как обнаружить |
|:--:|:--|:--|:--|
| A1 | **Z3 — не верифицирован формально** | KERN доверяет вердиктам Z3 (`unsat`/`sat`). Баг в самом Z3 → ложный вердикт | `tools/solver_crosscheck.py` (сверка с cvc5) |
| A2 | **Proof-checker разбирает вывод Z3, но не Alethe** | `proof_check.zig` перепроверяет вывод математически: запрет дыр (`hole`/`trust`/`sorry`), привязка каждого `asserted` к клаузе контракта, структура `mp`, покрытие литерал в `unit-resolution`, арифметика сертификата Фаркаша, обязательный корень `false`. ОСТАЁТСЯ: (а) Alethe/LFSC этой сборкой Z3 не порождается (`strings z3 \| grep -ic alethe` = 0, параметра `proof.format` нет) — проверяется только нативный формат; (б) шаги `rewrite` не перепроверяемы без реписания рерайтера Z3 и учитываются отдельно как `trusted_steps` | `src/verifier/proof_check.zig`; `docs/METRICS.md` §48 |
| A3 | **Нелинейная вещественная арифметика** | Z3 неполон для QF_NRA: возможен ответ `unknown` → трактуется как `e=0` (безопасно) | `src/verifier/nra_quant.zig` |
| A4 | **Кванторы** | Для формул с `forall`/`exists` возможен `unknown`/таймаут | `src/verifier/nra_quant.zig` |
| A5 | **Рекурсия/циклы** | Глубина обхода ограничена топливом (`fuel`). Циклы доказываются через CHC, но не любой формы | `src/verifier/chc.zig`, `src/runtime/kern_x.zig` |
| A6 | **Абстрактная интерпретация — интервалы** | Домен — только интервалы (не октаэдры/полиэдры): теряет корреляции между переменными | `src/verifier/abstract_interp.zig` |

## B. Ограничения формата и целостности

| # | Ограничение | Что это значит | Как обнаружить |
|:--:|:--|:--|:--|
| B1 | **Merkle покрывает только таблицу** | Подмена **содержимого** ловится отдельной сверкой `SHA-256(payload) == digest`, а не деревом | тест `ФИКС ЦЕЛОСТНОСТИ: подмена payload отвергается` |
| B2 | **zstd (`0x01`) не реализован** (сжатие `deflate` `0x02` — РЕАЛИЗОВАНО) | В Zig std есть только zstd-распаковщик; статической `libzstd.a` нет, линковка сломала бы герметичную musl-сборку. | B3 | **`hash_algo` = SHA-256** | Спецификация упоминает BLAKE3; реализация — SHA-256 (один алгоритм для сквозной сверки) | поле 20..24 заголовка |
| B4 | **Нет контроля версии схемы объектов** | `schema_version` объекта читается, но не валидируется | `src/core/object_entry.zig` |
| B5 | **Лимит размера артефакта** | Файл > 1 МБ в `kernc build` → пустой объект + предупреждение | вывод `kernc build` |

## Правило KERN при неопределённости

Во **всех** случаях из списков выше поведение системы — **fail-closed**:

| Ситуация | Результат |
|:--|:--|
| Решатель недоступен | `ToolError` → `e = 0` |
| Таймаут решателя | `e = 0` (жёсткий таймаут, поток-убийца) |
| `unknown` от Z3 | `e = 0` |
| Крах подпроцесса решателя | KERN жив, `e = 0` |
| Нет контракта у заявления | `e = 0` |

> **Ни одно ограничение не приводит к ложному `e = 1`.**
> Это проверяется тестами `z3_crash_test`, `smt_stress`, `mcdc_gates_test`.

## 8. Бакет `skipped` в `--xray`: 103 пропуска на `cmark-gfm/src`, разобранные по причинам

Измерено 2026-11-24 на `github/cmark-gfm` `7fe8904` (28 файлов `.c` в `src/`):

```
функций 308: checked 79 | trivial 126 | skipped 103   (Σ == total)
уровень ВЕТКИ (в skipped не входит): 2300 заметок
```

| N | Причина, дословно из вывода | Доля | Цена фикса |
|--:|:--|--:|:--|
| **54** | «условие не зарегистрировано как путь — **причина в ветвях регистрации не названа**» | 52 % | **дорого**: это не синтаксис, а отсутствие инструментирования регистрации ветвей; нужен дамп того, почему ветвь не попала в путь |
| **22** | «бинарный оператор (только `+ - * / // %`)» | 21 % | **дёшево**: `&&`, `\|\|`, `&`, `\|`, `^`, `<<`, `>>` переводятся в BV теми же правилами, что уже есть |
| **9** | «логическое отрицание `!` в форме, которую не переводим» | 9 % | **дёшево**: `!p` уже переводится как `p == 0` (#409), осталось покрыть `!(a && b)` и `!f(x)` |
| **8** | «индекс массива не литерал окна — гард не переводим (#570)» | 8 % | средне: нужен символический индекс, а не окно |
| **8** | «синтаксис Python после перевода C-like» | 8 % | средне: дамп конкретной строки, которую переводчик испортил |
| 2 | нет целочисленных параметров / сравнение nil вне Int-модели | 2 % | честная граница |

**Дешёвая часть: 31 из 103 (30 %)** — два механических правила (бинарные операторы и `!`).
**Дорогая часть: 54 из 103 (52 %)** — не синтаксис C, а собственная дыра трассировки ветвей.

### 8.1 Дефект, найденный при снятии этого дампа

Печатная гистограмма обрезается на десяти причинах:

```python
for key, cnt in sorted(reasons.items(), key=lambda kv: (-kv[1], kv[0]))[:10]:
```

Из 103 пропусков **названы 64, остальные 39 отброшены без строки «… ещё N»**. Это тот же
класс, что `#400`/`#401` (сводка обещает полноту, печать её не даёт). Полный список доступен
только через `--xray-json` (`skipped[].reason/count`, 49 записей, Σ = 103) — и именно оттуда
взята таблица выше. Требуется: либо печатать хвост строкой «… ещё N причин, M функций»,
либо сделать `--xray-json` обязательным для любого заявления о причинах.

### 8.2 Характерные примеры (дословно из условий)

1. `node == NULL` — сравнение указателя; `NULL` вне Int-модели, путь не регистрируется (вклад в 54).
2. `parser->first_nonspace <= parser->offset` — поле структуры, которое может изменить вызов; #527 (вклад в 54).
3. `S_last_line_checked(node)` — вызов в условии: значение невыводимо, ветвь честно не объявляется мёртвой (#525).

### 8.3 Разбивка 54 случаев «причина не названа» (`KERN_DEBUG_XRAY_SKIP=1`, #658)

Измерено на том же корпусе (`7fe8904`, `src/`). Диагностика включается **только** переменной
окружения; дефолтный `--xray-json` и его ABI не меняются (поле `drop_details` появляется
исключительно под `KERN_DEBUG_XRAY_SKIP=1`).

Сумма разбивки = **54** — ровно тот бакет, который раньше назывался «причина не названа»:

| N | `tag_from_text` | Что это | Что делать |
|--:|:--|:--|:--|
| **23** | `pointer_null_cmp` | `node == NULL` (15 из 23), `ref != NULL` — сравнение указателя, `NULL` вне Int-модели | **шаг 2**: сравнение указателя уже моделируется как `p == 0` (#409); нужно пустить его в РЕГИСТРАЦИЮ пути, а не только в гард |
| **9** | `struct_field_access` | `parser->root`, `parser->partially_consumed_tab` | средне: поле структуры, изменяемое вызовом (#527) — честная граница, пока нет модели псевдонимов |
| **8** | `logical_op` | `a && b` — конъюнкция не регистрируется как путь | **шаг 2**: `&&`/`\|\|` → `and`/`or` поверх уже поддержанных условий |
| **5** | `call_in_cond` | `peek_char(subj)` | дорого: межпроцедурно, честная граница (#525) |
| **3** | `string_literal_cmp` | сравнение с `'\r'`, `'-'`, `'.'` | **шаг 2**, дёшево: символьный литерал — это `Int` |
| **3** | `other` | не классифицировано текстом | требует ручного разбора |
| **2** | `negated_var` | `!node`, `!buf->size` | **шаг 2**: `!p → p == 0` (#409) |
| **1** | `bitwise_op` | побитовое в условии | **шаг 2**: QF_BV, с оговоркой про UB сдвига |

**Вывод для шага 2:** 23 + 8 + 3 + 2 + 1 = **37 из 54 (69 %)** закрываются теми самыми
дешёвыми правилами (`&&`/`\|\|`, `!`, указатель как `Int`, символьный литерал). Только 9
(поля структур) и 5 (вызовы в условии) остаются честной границей.

**Оговорка, которую нельзя терять:** `tag_from_text` — это классификация **текста** условия
(первое неподдержанное подвыражение слева направо), а **не** трассировка точки возврата внутри
парсера. Для последней нужен отдельный дамп, и он не делался.

### 8.4 Воронка регистрации и ПРАВДА о причине (дефекты #660/#661)

Измерено на `7fe8904`, `src/` (28 `.c`), счётчики под `KERN_DEBUG_XRAY_SKIP=1`:

```
найдено if (...):                2538
  отброшено как nil/null:           3
  отброшено как `!`:               16
  отброшено как «не переводится»:  123
зарегистрировано в if_blocks:    2386   ← 94 %
функций без единой регистрации:    16   (из 182 функций с `if`)
```

**Гипотеза «однострочные `if` без `{}` теряются» ОПРОВЕРГНУТА.** В cmark-gfm 3500 из
5201 условий (67 %) записаны без фигурных скобок — и 94 % всех условий всё равно
регистрируются. `_clike_block_end` бесскобочные блоки обрабатывает.

**Отсюда дефект #661:** ветка «решатель не спрошен» печатала
«условие не зарегистрировано как путь — причина в ветвях регистрации не названа».
Это было **ложно** в 87 случаях из 103: пути зарегистрированы, вопрос не дошёл до
решателя. Теперь причина называется по факту, три состояния:

| Условие | Что печатается |
|:--|:--|
| `if_blocks` пуст | «условие не зарегистрировано как путь (первое: …)» |
| пути есть, целочисленных параметров нет | «нет ЦЕЛОЧИСЛЕННЫХ параметров — пути зарегистрированы, но обязательств в Int-модели не возникло» |
| пути есть, `params` есть, решатель не спрошен | «все зарегистрированные ветви отсеяны как НЕВЫВОДИМЫЕ (вызов/поле структуры/нет обязательств)» |

Регресс-тест: `tools/xray_skip_reasons_check.py` → `_check_attribution()` проверяет все
три состояния и падает, если ложная формулировка вернётся при непустых `if_blocks`.

**Новая гистограмма на том же корпусе (`skipped 103`, сумма сходится):**

| N | Причина | Что это значит |
|--:|:--|:--|
| 54 | все зарегистрированные ветви отсеяны как НЕВЫВОДИМЫЕ | условия зависят от вызовов/полей — честная граница (#525), НЕ дефект парсера |
| 22 | бинарный оператор (только `+ - * / // %`) | расширение BV-операторов |
| 9 | логическое отрицание `!` | `!ptr → ptr == 0` (Правило 4) |
| 8 | индекс массива не литерал окна (#570) | символический индекс |
| 8 | синтаксис Python после перевода C-like | нужен дамп испорченной строки |
| 2 | нет Int-параметров / nil вне Int-модели | честная граница |

### 8.5 Что НЕ утверждается

`checked 79` не означает «остальные 229 безопасны»: `trivial` — нет обязанностей,
`skipped` — не анализировались. Находок на этом прогоне 0, и это ноль **при 103 пропусках**,
а не при полном покрытии.

## 9. Кандидат, ОТКЛОНЁННЫЙ после проверки достижимости (2026-11-24)

Найден залпом по формам E/F и разобран до конца, но **репортом не стал**. Записан,
чтобы следующая сессия не проходила этот путь заново.

**`Enlightenment/efl` `src/lib/eet/eet_image.c:664`** — `eet_data_image_lossless_convert`:

```c
d = malloc((w * h * 4) + 32);            // w=h=32768 -> w*h*4 == 2^32 == 0 -> 32 байта
memset(d, 0, 32);
header[1] = w; header[2] = h;           // заголовок заявляет 32768 x 32768
memcpy(d + 32, data, w * h * 4);        // копирует 0 байт: то же произведение
_eet_image_endian_swap(header, w*h + 8); // пишет 4*(w*h+8) байт — но ТОЛЬКО на big-endian
*size = (w * h * 4) + 32;               // 32
```

Репро (изолированное, ASan): `malloc=32, w*h*4=0`; на little-endian `rc=0`,
на принудительном big-endian — `ERROR: AddressSanitizer: heap-buffer-overflow`.

**Три причины НЕ отправлять:**

1. `w`,`h` — **параметры публичного API**, а не поля файла: это не класс `iio`
   (там размеры приходили из заголовка). Ответ «caller must pass valid dims» законен;
2. порча памяти только при `_eet_image_words_bigendian` (big-endian хост); на x86
   остаётся лишь заголовок с выдуманными размерами и `*size = 32`;
3. у репозитория **нет** `SECURITY.md` / `CONTRIBUTING.md` (проверено: 404), то есть
   нет и канала приватного репорта — заявка ушла бы публично.

**Что было бы нужно, чтобы кандидат стал репортом:** вызывающий, который передаёт сюда
размеры, прочитанные ИЗ ФАЙЛА, без проверки магнитуды. Такого звена в дереве EFL не найдено.

## 10. Точечный аудит трёх академических C-проектов: измеренный потолок (2026-11-25)

Отбор по четырём признакам профиля `iio`: чистый C/C++, разбор бинарных или научных
данных, отсутствие OSS-Fuzz, активность 2025–2026. Прогон — по **всем** своим файлам
дерева (vendored исключены), формы `A/B/D` + новые `E/F`.

| Проект | HEAD / активность | Файлов | Срабатываний | Пригодных |
|:--|:--|--:|--:|--:|
| `rordenlab/dcm2niix` | `e66d2f3`, 2026-10-29 | 21 (своих 6) | **0** | 0 |
| `neurolabusc/nii2mesh` | `b148e4b`, 2026-04-08 | 24 | **0** | 0 |
| `DCMTK/dcmtk` (`dcmdata/libsrc`) | 2026-11-25 | 98 | **1** | 0 |

**Единственное срабатывание и почему оно снято.** `dcddirif.cc:4549`:

```c
if ((pgmWidth > 0) && (pgmHeight > 0) && (pgmWidth <= 0xffffu) && (pgmHeight <= 0xffffu)) {
    const unsigned long pgmSize = pgmWidth * pgmHeight;   // ≤ 65535² = 4 294 836 225 < 2³²
    Uint8 *pgmData = new Uint8[pgmSize];
```

Границы проверены ОБЕ и до умножения, тип `unsigned long` (64-бит на LP64), максимум
произведения помещается даже в 32 бита. Класс `iio` здесь не достигается.

**Что это говорит о детекторе (честная точность на этом срезе):** 1 срабатывание,
0 пригодных. Причина снятия названа: наш гард-фильтр ищет `SIZE_MAX/` и каст, но не
узнаёт парную проверку `(w <= 0xffffu) && (h <= 0xffffu)` на двух множителях. Это
калибровка, которую МОЖНО добавить; до неё такие кандидаты требуют ручного чтения.

## 15. `pydantic` NaN round-trip: НЕ дефект, осознанный компромисс (проверено до репорта)

Наблюдение (3 строки): `F.model_validate_json(F(f=nan).model_dump_json())` падает, потому
что дефолт `ser_json_inf_nan="null"` пишет `{"f":null}`, а поле `f: float` принимает только
число. Выглядит как нарушение `decode(encode(x)) == x`.

**Проверено ДО любого обращения в трекер (урок `typst#9103`/`gleam#6524`):**

| Проверка | Результат |
|:--|:--|
| трекер `pydantic/pydantic` по `ser_json_inf_nan` | **#10037 open** «`model_dump(mode="json")` can output non-serializable NaN», **#12260 open** «Unions do not respect `ser_json_inf_nan`», **#13996 closed** — тема известна и активно ведётся |
| `ser_json_inf_nan="strings"`, lax | `{"f":"NaN"}` → чтение **OK** (`nan`) — штатный round-trip-режим |
| `ser_json_inf_nan="strings"`, `strict=True` | **падает** `float_type`, потому что strict-режим отключает приведение `str -> float` — это его документированная семантика |
| `bytes(b"\xff\xfe")` | `PydanticSerializationError` — bytes не представимы в JSON |

**Вердикт: НЕ репорт.** `null` — единственное RFC-8259-совместимое представление
нечислового float, выбор сделан осознанно и уже обсуждается в открытых тикетах;
`strings` — документированный обход для round-trip, а его поведение в `strict=True`
следует из определения strict. Отправка была бы четвёртым «закрыто как задумано».

**Что осталось верным измерением:** `-0.0`, `2**63`, `-(2**63)-1`, `Decimal("1E+3")`,
`Decimal("1.500")`, `Union[int,bool]` (`1` -> `1`, `True` -> `true`), `Literal[1, True]`,
`datetime` наивный и `+00:00` — **все прошли round-trip**. TOML (`tomli-w`+`tomllib`,
`tomlkit`) на корпусе `\r`, управляющих символов, `2**63`, `nan`, `inf`, пустых таблиц — **0 расхождений**.

/* B: без исчерпания — находка ОБЯЗАНА остаться */
