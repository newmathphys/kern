## Механизм (что именно добавлено)

1. **Bounded AST unrolling (K = 2, `KERN_UNROLL_K`)** — `while cond: body` и
   `for i in range(...)` разворачиваются в K копий тела. Это **недо-аппроксимация**:
   годится для поиска контрпримеров, но НЕ для доказательства.
2. **Ограниченный inline саморекурсии** — тело функции подставляется с
   фактическими аргументами на K шагов; на дне бюджета вызов становится havoc.
3. **Live Replay** — каждый SAT-кандидат проверяется РЕАЛЬНЫМ вызовом
   `buggy_fn(**args)` и `correct_fn(**args)` (таймаут 2 с, лимит рекурсии 300,
   перебор малого домена для несвязанных аргументов). `DIVERGED` — только при
   реальном расхождении; иначе `DISCARDED`. Это гарантия **0 ложных обвинений**.
4. `import` / `AnnAssign` / `a, b = e1, e2` / `x op= e` — No-Op или точная
   трансляция вместо `SKIP`.

## Update после дефекта #209 (списочный домен Live Replay)

**Причина прошлого «DISCARDED»:** домен `_confirm()` состоял ТОЛЬКО из `int`

## Update после схемы списков в чистом Int (defect #212: `arr[i]`, `for x in arr`)

**Причина прошлых SKIP:** `arr[i]` (`ast.Subscript`), `arr[i] = v`, `for x in arr`
и `while n:` (число в позиции `Bool`) были вне подмножества — 10+ задач
уходили в SKIP ДО решателя.

**Сделано (без теории массивов, чистый `QF_LIA`):** окно `arr__e0..arr__e2 : Int`
+ `len__arr : Int`; чтение `arr[i]` -> каскад `ite`; запись и `arr[i] += v` ->
обновление трёх `ite`; `for x in arr` -> `for i in range(len(arr))` развёрнутый
на K шагов под условием `len__arr > t`; `if n:` / `while n:` -> `(not (= n 0))`,
`if arr:` -> `(> len__arr 0)`. Это ОВЕР-аппроксимация, поэтому `DIVERGED`
по-прежнему заявляется ТОЛЬКО после живого вызова обеих версий (#206).

**ИЗМЕРЕНО (QuixBugs, 40 задач):**

| | было (#209) | стало |
|:--|--:|--:|
| DIVERGED (живой вызов) | 3 | **5** |
| DISCARDED | 2 | 3 |
| SKIP | 35 | 32 |

Новые подтверждённые баги: `hanoi` (`height=1, start=0, end=0`: `buggy=[(0,1)]`
vs `correct=[(0,0)]`) и `sieve` (`max=2`: `buggy=[]` vs `correct=[2]`).
Оба — реальные дефекты датасета, подтверждены исполнением.

**Контроль отсутствия ложных обвинений:** `find_in_sorted` при `binsearch`
дал `DIV-DISCARDED(не загрузить)` — кандидат отброшен, а не заявлен.

## Update после восстановления списка ИЗ МОДЕЛИ Z3 (defect #216)

**Причина прошлого `DISCARDED` у `max_sublist_sum`:** модель Z3 содержит
элементы окна (`arr__e0`, `arr__e1`, `arr__e2`) и `len__arr`, но НЕ сам
список `arr`, поэтому `p in model` для него не срабатывал, а в запасном
домене не было списка, начинающегося с отрицательного числа.

**Сделано:** в `_confirm()` список собирается ИЗ МОДЕЛИ —
`arr = [arr__e0, arr__e1, arr__e2][:len__arr]` (+ домен пополнен
`[-1,2]`, `[2,-1,2]`, `[1,-2,3,-1]`). Подтверждение по-прежнему ТОЛЬКО
живой вызов обеих версий.

**ИЗМЕРЕНО:**

| | было (#214) | стало (#216) |
|:--|--:|--:|
| DIVERGED (живой вызов) | 5 | **6** |
| DISCARDED | 3 | **2** |

Новый подтверждённый баг: `max_sublist_sum` — при `arr=[-1, 2]` багованная

**Что дало +1 к 32.** Раньше `call()` считал падение «нерасхождением», если тип исключения
входил в список ожидаемых (`TypeError`, `ValueError`, …), — из-за этого исключение,
поднятое **внутри тестируемого кода**, глушилось. Теперь критерий иной: смотрим **кадр
трассировки** (`_raised_in_target`) — если исключение родилось в файле самой задачи,
это её падение, и оно фиксируется как расхождение с `ok`.

| Задача | Вход | buggy | correct | суть |
|:--|:--|:--|:--|:--|
| `bitcount` | `{'n': 1}` | **не завершается** (бесконечный цикл) | `1` | `while n: n ^= n - 1` — неверная битовая операция зацикливает счётчик |

Свидетельство независимо перепроверено без движка: `buggy(1)` не завершается и за 5 с,
`correct(1)` возвращает `1` (значение подтверждено отдельным запуском).
